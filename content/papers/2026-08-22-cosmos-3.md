## 研究问题

Physical AI 需要同时具备**理解**和**生成**两个能力，具体靠三类设计：各模态自己的 encoder、结构化的 token 排布，以及 Mixture-of-Transformers backbone——用它把自回归推理和 diffusion 生成耦合在一起。

![Cosmos 3 统一多种模型类别](media/cosmos-3/figure1-omnimodal.png "图 1｜论文 Figure 1：Cosmos 3 同时建模 language、image、video、audio 和 action，覆盖理解和生成，从而把 VLM、图像生成、音视频生成、policy / WAM、forward dynamics 和 inverse dynamics 收进同一套网络。来源：Cosmos 3。"){.scale90}

比如论文举的收拾餐桌的例子：

基于当前的camera observation先给 VLM：

$$\text{VLM} \rightarrow \text{识别盘子在哪里 + 规划}$$

再给 VLA/WAM：

$$\text{VLA/WAM} \rightarrow a_{1:T}$$

如果还想判断这个动作执行以后会发生什么，又要：

$$\text{World Model} \rightarrow v^{\text{future}}_{1:T}$$

$$\text{Perception} \rightarrow \text{Planning} \rightarrow \text{Action} \rightarrow \text{World Simulation}$$

是好几个独立模型串起来。

Cosmos 3 想把它变成：

$$(\text{text, image/video, audio, action}) \longleftrightarrow \text{one backbone}$$

换一个 input/output arrangement，同一个模型就能做 VLM、video generation、forward dynamics、inverse dynamics、policy。论文精确说它希望“不改 architecture”就能在这些模式之间切换。

> **Q1：** 这三步是不是被强行拆开的？
>
> 虽然这里分了3步，但是我感觉是强行分的，强理解vla也有vlm能力，预测未来画面wam也有能力。有点奇怪🤔，感觉就是想表达，分开的model单独串起来knowledge不共享，所以想引出omnimodal的重要性而已。

> **Q2：** one backbone 之后步骤也没少，shared feature 的好处到底在哪？
>
> 还是同一个模型把原来几件事都做了，pipeline 长度没变。收益只是难道“少部署几套权重”，并且同时希望“真正共享 world representation”。不确定有没有 ablation 证明：jointly 训过的 representation，比把现成 VLM + WAM/ VLA 拼起来更好。但是貌似小红书测试的人说[forward dynamic不如lingbot video，policy效果不如 pi0.5？](https://xhslink.cn/o/AHLcKNv4cqY)

## 核心方法
> [!NOTE]
> **核心问题：** Cosmos 3 到底怎么把 VLM、视频生成、音频生成和 action generation 塞进同一个模型里？

### 1. Encoders--各种模态如何编码成token的？

先把所有模态变成 token。输入可能有 text、image/video、audio、action，但编码方式不同：

- **text**：正常 language token
- **image/video（理解）**：ViT encoder
- **image/video（生成）**：Video VAE latent
- **audio**：Audio VAE
- **action**：连续 action vector 经线性 projection 变成 action token

> [!NOTE]
> **Action是怎么统一表示成action representation？再投影成action token的？**

![统一 action representation](media/cosmos-3/figure3-unified-action.png "图 3｜论文 Figure 3：把异构 embodiment 的控制映射成由共享几何部件拼起来的紧凑 action vector。Ego / effector 用相对位姿伪动作表示（3D 平移 + 6D 旋转；旋转自由度实际是 3，6D 是 Zhou et al. 2019 的过参数化）。Grasp state 直接编码当前抓取状态：人手用指尖位置，机器人用夹爪开合。不同长度的 action vector 再用 domain-aware in/out projection 投到共享语义空间。来源：Cosmos 3。"){.scale90}

**a) action 怎么统一表示？**

原始控制本身是多样的：车是 steering / throttle / brake，机器人是 joint angle / gripper，人是 head / wrist / fingers。Cosmos 3 先把不同 embodiment 的控制改写成同一套几何语义，这一步叫 Action Representation，指的是 **Projection 之前** 的那个向量：

$$
\text{Action} = \text{Ego Pose} + \text{Effector Pose} + \text{Grasp State}
$$

大概理解就是："我怎么动 + 手怎么动 + 手现在什么状态。"

- **Ego Pose**：主体或相机怎么动。车往前开、头戴相机左转、机器人身体移动。表示成 3D 位移 + 6D 旋转。
- **Effector Pose**：真正操作物体的那一端怎么动。夹爪、人手腕。同样是 3D 位移 + 6D 旋转。
- **Grasp State**：手现在张开还是抓住。夹爪通常 1D（开/合），人手用五指位置，大约 15D。

车、人、机械臂、humanoid 都能拆成「主体运动 + 操作端运动 + 抓取状态」，所以表达方式能统一。但 **长度还没统一**：有的只有 ego，有的还有双手和手指。

**b) action vector 怎么变成 token？**

整条链路是：

$$
\text{原始控制} \rightarrow \text{Action Representation} \rightarrow \text{Projection} \rightarrow \text{Transformer token}
$$

长度不同的向量进不了共享 backbone，所以每个 embodiment 用自己的 **domain-aware in/out projection**，把变长 action vector 投到同一 hidden size。解码时再投回各自原来的 action 空间。


### 2. Token 排布——不同任务怎么有秩序地摆进同一个 Cosmos 3？

核心思想就是约定一种固定顺序，把所有模态、所有任务都有秩序地拼成一条序列送进 Cosmos 3。

总结构如下：

$$
S = [S_{\mathrm{AR}},\ S_{\mathrm{DM}}]
$$

- $S_{\mathrm{AR}}$：**理解 / 推理部分**，放 language 以及经过 ViT 的 image/video；用 **causal attention mask**。
- $S_{\mathrm{DM}}$：**生成部分**，放 VAE vision、audio、action；用 **双向 attention mask**。

摆放规则总共就 3 条：

$$
\text{AR} \mid \text{DM clean} \mid \text{DM noisy}
$$

1. **AR 永远放最前面。**
2. **DM 里**，作为条件的 clean token 放前面，要生成的 noisy token 放后面。
3. **DM 中不同 modality 的固定顺序**是：vision → audio → action。

于是任何任务都能统一写成（clean DM = 已知条件，noisy DM = 生成目标）：

$$
[S_{\mathrm{AR}},\ \text{clean condition},\ \text{noisy target}]
$$

按这套规则，各任务只是往里填不同的 clean / noisy token：

| Task             | Paper Form                                                       | Clean / Condition               | Noisy / Target            |
| ---------------- | ---------------------------------------------------------------- | ------------------------------- | ------------------------- |
| VLM              | $S_{\mathrm{AR}}$                                                | image/video + text              | text next token           |
| T2I              | $[S_{\mathrm{AR}}, \tilde v_1]$                                  | text                            | image                     |
| T2V              | $[S_{\mathrm{AR}}, \tilde v_{1:N}]$                              | text                            | video                     |
| T2V + Audio      | $[S_{\mathrm{AR}}, \tilde v_{1:N}, \tilde s]$                    | text                            | video + audio             |
| I2V / V2V        | $[S_{\mathrm{AR}}, v_{1:P}, \tilde v_{P+1:N}]$                   | text + observed video $v_{1:P}$ | future video $v_{P+1:N}$  |
| Video Transfer   | $[S_{\mathrm{AR}}, v^{\mathrm{ctrl}}_{1:N}, \tilde v_{1:N}]$     | text + control video            | target video              |
| Forward Dynamics | $[S_{\mathrm{AR}}, v_{1:P}, a_{P+1:N}, \tilde v_{P+1:N}]$        | text + context video + action   | future video              |
| Inverse Dynamics | $[S_{\mathrm{AR}}, v_{1:N}, \tilde a_{2:N}]$                     | text + before/after video       | action                    |
| Policy           | $[S_{\mathrm{AR}}, v_{1:P}, \tilde v_{P+1:N}, \tilde a_{P+1:N}]$ | text + context video            | **future video + action** |


### 3. MoT：拼好的 [AR, DM] 序列，进入 Transformer 以后到底怎么处理？

双塔结构：每一层有两套参数，Reasoner tower 处理 AR reasoning，generator tower 处理 DM generation，只在 self-attention 处交互，具体如图。

![Cosmos 3 的 MoT 架构与 attention mask](media/cosmos-3/figure5-mot-architecture.png "图 4｜论文 Figure 5：MoT 双塔与 attention mask。AR 塔和 DM 塔各有独立 LayerNorm / MLP，只在 shared self-attention 相遇；关键就在右边的 mask：$Q_{\mathrm{AR}}$ 只做因果自注意力（看不到 DM），$Q_{\mathrm{DM}}$ 则对 $[K_{\mathrm{AR}};K_{\mathrm{DM}}]$ 全注意力，所以 diffusion 以 AR 为条件、而 AR 只看自己。来源：Cosmos 3。"){.scale90}

***模型架构：*** 基本上是分为几种架构Edge、Nano、Super，基本定位分别是--端侧部署、中等算力、高质量生成
> 需要注意的是双塔结构，导致总参数量是两倍的体量。
> 
> Q: 但是这里会产生一个直接的问题？？同样是32B的参数量，VLM的模型表现可能比video diffusion model的好的多。。。一定要求同参数量感觉有点没必要。。

![Cosmos 3 的 MoT 模型变体](media/cosmos-3/table2-model-variants.png "图 6｜论文 Table 2：Cosmos 3 的 MoT 变体。三档都是双塔，每层 reasoner / generator 各有一套参数。Edge 是 2B dense 从零训（合计 4B）；Nano / Super 分别从 Qwen3-VL-8B / 32B 初始化（合计 16B / 64B）。来源：Cosmos 3。"){.scale90}

### 4. 位置编码怎么设计？

> [!NOTE]
> 各种模态可以按照 (t,h,w) 编码就好，但是 video、audio、action 的采样频率都不一样，怎么让它们在 attention 里知道“谁和谁发生在同一真实时间”？

其实只需要记三件事：

1. 所有 modality 用 $(t,h,w)$ 的 3D MRoPE。
2. video / audio / action 的 $t$ 按真实采样率缩放。$\delta t = \mathrm{TPS}_{\mathrm{base}} / \mathrm{TPS}$，含义是每走一个 token，position 里的时间增加多少。
3. AR 和 DM 的 temporal position 中间空 $15000$。


![Cosmos 3 的 3D MRoPE 坐标分配](media/cosmos-3/figure6-mrope-coordinate.png "图 5｜论文 Figure 6：3D MRoPE 的坐标分配。每个 token 拿一个 $(t,h,w)$：language 用 $t=h=w$，video 三个轴都变，audio / action 只有时间轴（$h=w=0$），文本和视觉的时间范围用一个 modality offset $k$ 隔开。右边的 FPS modulation 把帧号映射到缩放后的时间位置，让 16 / 24 / 30 FPS 下相同真实时长占相同的位置区间（24 FPS 为 base）。来源：Cosmos 3。"){.scale90}


举个例子，取 $\mathrm{TPS}_{\mathrm{base}}=6$（24 FPS 视频、VAE 时间压缩 4 倍）：

- **video**：24 FPS / 4 $= \mathrm{TPS}_{\mathrm{video}}=6$，所以 $\delta t_{\mathrm{video}}=6/6=1$，时间位置是 $0,1,2,3,4,5,6,\ldots$
- **action**：假设 10 Hz，$\mathrm{TPS}_{\mathrm{action}}=10$，所以 $\delta t_{\mathrm{action}}=6/10=0.6$，时间位置是 $0,0.6,1.2,1.8,2.4,3.0,\ldots$

同一真实时刻（比如 $t=3$）上，video 的第 3 个 token 和 action 的第 5 个 token 会对齐。

### 5. 训练过程？分为4个过程的逐阶段训练

> Cosmos 3 不是一开始就把所有 modality 一锅端训练，而是先学 reasoning，再学通用 world generation，最后才加入 action，让已有的 video dynamics prior 逐渐转化为 controllable world-action knowledge。
> 
> 需要注意的是：训练generator时候，reasoner是frozen的，另外之所以不用VDM-wan 2.1等去初始化generator，使用Reasoner，是为了继承“世界语义表示”，同时让两个 tower 从一开始就在同一个 representation basis 上；真正的 video-generation prior 再靠后续大规模 diffusion pretraining 学出来。

训练基本过程如下：

```
Reasoner Pretrain + SFT
        │
        │ initialize Generator
        ▼
Generator Pretrain
(Image + Video + Audio)
        │
        │ + Action
        │ + Physical AI Data
        ▼
Mid-training
(World + Action)
 ├─ Forward Dynamics: (v_past, a) → v_future
 ├─ Inverse Dynamics: (v_past, v_future) → a
 └─ Policy: v_past → (v_future, a)
        │
        ▼
Post-training
(T2I / I2V / Robot Policy)
```

### 1.1 预训练阶段数据清洗流程
该阶段数据主要来源于 Nemotron Nano 2 的 19.7M，和额外整理的 2.3M 数据（补数学、视频、空间定位和指令跟随）。整条链路两步：**语义去重 → AI 质量过滤**：

```
19.7M 通用数据 + 2.3M 补充数据
        ↓
完整 conversation 联合 embedding
        ↓
K-means 粗分组 + 组内余弦去重 (> 0.95)
        ↓
Gemma Judge：Faithfulness / Completeness / Correctness
        ↓
min(s_F, s_C, s_R) ≥ 2
        ↓
22M Reasoner 预训练数据
        ↓
ViT + Projector + LLM 联合 next-token 训练
```

**① 语义去重（semantic deduplication）**

对话级别的去重: 核心是把媒体和文本的联合编码表示拼起来（即问题和答案都一样的情况）

$$
e_i = \mathrm{Combine}(e_i^{\mathrm{media}},\ e_i^{\mathrm{text}})
$$

不同的模态使用不同的编码器：Image-text / Text-only 用 Qwen3-VL-Embedding-8B，Video-text 用 PE-Core-G14-448。

为了在生产规模上算得动，先用 K-means 粗分组，再在组内用 cosine 相似度精确去重，相似度 > 0.95 的删掉。这一步去掉约 4.23%。

**② AI 质量过滤（AI-judge quality filtering）**

用 Gemma-4-31B-it 当 data auditor，对每个 conversation 的三个维度分别打 1∼5 分：

- **Faithfulness**：回答是否都有图 / 视频 / 文本依据（防幻觉，对 Cosmos 3 最关键）
- **Completeness**：是否完整回应了指令，没有重要遗漏
- **Correctness**：事实、逻辑、任务层面是否正确

保留规则看**最差维度**而不是平均维度：

$$
\min(s_{\mathrm{F}},\ s_{\mathrm{C}},\ s_{\mathrm{R}}) \geq \tau
$$

> [!NOTE]
> **经验总结**
>
> - 按完整 conversation 语义去重，而不是只按图片去重，大概去掉 4.23%。
> 
> - 质量过滤看最差维度，不用平均分掩盖严重错误。
> 
> - 预训练用较宽松阈值保覆盖，SFT 用严格阈值保精度。
> 
> - 阈值 $\tau$ 的用法：预训练如果直接用 $\tau=5$ 的高质量数据，分布会极不均衡，某些任务几乎被完全忽略（如 referring grounding 被删得最狠）；所以预训练取 $\tau=2$，只删明显错误、尽量覆盖各类任务，保留约 **78%**。SFT 阶段更看重精度，取 $\tau=5$，保留约 **46%**。

### 1.2 SFT 阶段新增了哪些任务数据？
共 2.2M 样本，分两大块：先补**通用空间 + 时间理解**，再针对**自动驾驶、机器人、智慧基础设施**三个垂直域做专门数据。（注意，这部分太碎太细了无法统一总结，下面是claude opus 5总结的表格）

| 领域 | 新增的任务 | 数据怎么来的 |
| --- | --- | --- |
| 通用空间理解 | 2D/3D grounding、pointing、计数、轨迹、自由空间与可达性 QA、跨视角对应 | 2D 大头是 LocateAnything 里采高质量子集；3D 把 3D 扫描场景转成 camera-relative 3D box 的指令样本（直接监督最终 box，不走 2D→3D 串联）；还有一路答案直接从仿真器 state（相机、物体位姿、深度、mask、可行域）算出来，再用程序 + VLM critic 校验 |
| 通用时间理解 | 稠密时序 caption 与事件定位、物理合理性打分、结构化时空 upsampling | 人工标 atomic action + 起止时间（平均 1.8s / 14.2 词）；55K 视频（2.6K 小时）产出 743K 个「起始时间, 结束时间, caption」三元组；FoundationMotion pipeline 每个 clip 自动出 10 道四选一；物理合理性用人评的 13.5K (视频, 问题, 答案) + VideoPhy-2 的 3.4K 打分视频转成 QA |
| 自动驾驶 | 驾驶决策 CoT、事故/急刹等事件定位、3D 车辆 grounding | 内部驾驶日志里 10K+ 人标 CoT 打底，再用 SOTA VLM + ego 轨迹 + meta-action 自动扩到约 1.1M；事件定位来自 Nexar 行车记录仪 24K+ 视频；3D grounding 来自 MADS 多相机数据集按 ~1 FPS 抽帧 |
| 机器人 / Embodied | 末端执行器 2D waypoint 规划（Action-CoT）、子任务切分、长时规划、手术场景理解 | Action-CoT 用模块化流水线拼：Qwen3-VL-72B 出 grounding 与 move reasoning、Molmo-7B 做定位、轨迹目标取自 MolmoAct 或跟踪过的 DROID；另有 MimicGen 方向 3.6K Omniverse 重渲染视频、BEHAVIOR-1K 83K 长时规划样本、EO-Data-1.5M 的 ERQA；手术是 398K 多轮对话 / 2.2M 图像 |
| 智慧基础设施 | 仓库空间 QA、密集行人定位、交通碰撞与异常推理 | 仓库用 Omniverse 合成语料，从 93K RGB-D / 873K QA 里均衡抽 80K；行人是 208K 图、5.6M 人工标框（先打码再标注）；交通用 CARLA 合成碰撞 3.4K + TAR 的 3.6K 交通摄像头视频 / 44K 标注（层级 CoT 自动标再和人工交叉核对）+ 1K 内部监控 clip |

> [!NOTE]
> **经验总结**
> 
> - 数据获取就三种途径：**已有公开数据集重采样**、**从仿真器/日志的 state 直接算标签**、**VLM 批量打标 + 少量人工标注**。人工只花在最贵的地方（稠密 caption、行人框、驾驶决策种子）。
> 
> - 凡是自动标注都配一层校验：程序检查、VLM critic、和人工标注交叉核对。否则规模一上来，没校验把关的话，噪声就压不住。
> 
> - 任务格式先统一（box / point 都归一化成同一套 JSON），不同来源的数据才能混在一起训。


**问题？？ 那「统一成同一套 JSON」到底怎么统一的？** 
论文没给完整 schema，只说清了原则、有哪些字段，下面是Opus 5给的一个例子。

原始数据各家格式互不兼容：COCO 检测是像素 [x, y, w, h] 加一个数字类别 id；referring 数据集是像素 [x1, y1, x2, y2] 加一句话；pointing 数据集只给一个像素点；3D 扫描场景给的是世界坐标系下的 box，而且每个数据集自带一套相机参数。统一之后全都变成「问一句话，回一段 JSON」：

```
Q: Locate all the forklifts in the image.
A: [{"label": "forklift", "bbox_2d": [0.12, 0.34, 0.28, 0.61]},
    {"label": "forklift", "bbox_2d": [0.55, 0.30, 0.71, 0.58]}]

Q: Point to an empty spot on the table where I can put the mug.
A: [{"label": "free space", "point_2d": [0.47, 0.62]}]

Q: Where is the car in front of the ego vehicle?
A: [{"label": "car", "center": [1.2, 0.1, 14.7], "dimensions": [1.8, 1.5, 4.3],
     "orientation": [0.0, 0.02, 0.0]}]
```

对回三条原则就好懂了：这样的好处也很直接--- 十几种来源、十几种任务能一起塞进同一个 next-token 目标训练，解析和评测也只需要一个解析器就行。

1. **坐标归一化** ： 上面写的是 0~1 的比例而不是像素值，所以 1080p 和 720p 的同一个框长得一样；3D 则先把各家的相机内参和物体朝向对齐到统一约定（Omni3D / Cube R-CNN 的口径），让「14.7」在所有数据里都真的是 14.7 米。
2. **答案塞进同一组字段** ： 检测、referring、计数、pointing 的区别，只是字段用 bbox_2d 还是 point_2d、返回一个还是多个元素。输出的协议和格式只有一种。
3. **直接监督最终结构**：3D 那条的答案里直接就是 center / dimensions / orientation，而不是先让模型吐一个 2D 框、再交给另一个模块抬到 3D。

### 2.1 Pre-training 阶段数据

预训练数据就是最基本的图像、视频的过滤流程。基本上所有视觉数据的处理、标注和筛选流程都可以分为以下5步：

```
原始收集与预处理          TransNetV2 场景切分 → ffmpeg cropdetect 去黑边 → 统一转码
        ↓
Embedding + 去重        图编码用Qwen3-VL-Embedding-8B｜视频编码用 Cosmos-Embed1-448p
                        抽 147M 图 / 400M clip，各跑 cuML KMeans 20,000 簇，簇内余弦去近重
        ↓
分类 + 基础过滤          47 个层级类别（General + Physical AI）
        ↓
结构化 caption 标注      自研 Qwen3-VL-8B captioner，输出固定字段 JSON
        ↓
按分辨率 / 时长分 shard
```

**关键补充**
- Step 2：聚 2w簇是为了省计算量

- Step 3 图像过滤：aesthetic 过低、collage、水印、白底、NSFW等问题；合成图额外看 photorealism（练文字渲染的除外）。

- Step 3 视频过滤：三个 0–9 的质量分数（DOVER aesthetic / DOVER technical / VTSS）+ 约 100 种 artifact 标签。**严重的直接删**（分屏、旋转、静态）；**轻微的只打标签、预训练照样留**（叠字、动态模糊、压缩噪声）——宁可留点瑕疵来保证覆盖度，mid-training 再严格筛。

- Step 3 的 47 类标签：论文只说「47 个层级类别，含 General 和 Physical AI 两域」，**没给清单**，说是使用"a small suite of in-house VLM"来实现打标签和过滤的。47类标签的作用不是过滤，而是标注清楚每个概念有多少数据，从而可以实现概念上的均衡等等、mid-training 按域配比（43.9% 领域专用那种）、以及按域评测。

**最终规模：** 7.8B 原始图筛到 767M，3B 源视频处理成 347.7M clip（源视频会切成多段，所以后者不是留存率）。分辨率上 720p 占图 26.8% / 视频 36.4%，480p 占图 26.0% / 视频 30.8%，≥1080p 占图 25.2% / 视频 12.2%；宽高比 16:9 占图 52.0%、视频 97.3%，图像里第二多的是 1:1（25.2%）。四种训练模式的采样比见 Sec. 4.2.1：T2I 20% / T2V 56% / I2V 16% / V2V 8%，它们的唯一区别就是往样本前面拼几帧干净的条件帧。


**各个阶段的图像和视频数据配比概述如下：** 后面是具体的细节展开
| 阶段 | 图像 | 视频 |
| --- | --- | --- |
| 预训练 | 7.8B 原始图 → **767M**（约 1/10） | 3B 源视频 → **347.7M clip**（源视频会切成多段，所以这不是留存率） |
| Mid-training | 60% 真实 + 36% 合成 + 4% 文字渲染 | 46.0% 从预训练池严格筛的高质量 + 43.9% 领域专用（机器人 / 自驾 / 人类活动 / 第一人称手物交互）+ 10.1% 难例（人体运动、高速复杂运动、精细操作） |
| Post-training | 只留合成 + 文字渲染 + 高质量真实，**完全排除** web 级预训练数据 | 预训练池抽样当 regularizer 防过拟合 + SFT 视频（合成 / 人工精选真实 / 按 embedding 相似度检索回来的失败案例） |



### 2.2 Mid-training 阶段数据

和预训练要覆盖度不同，中期训练要的是两件事：一是用精挑的高质量数据把生成质量提上去，二是加新能力，既包括领域能力（Physical AI），也包括新任务（video transfer）。所以数据有三个来源：高质量真实图/视频、合成图/视频(包括Physical AI相关)、video transfer 数据。

① 高质量图像和视频，混合比例如下：

| 来源 | 图像 | 视频 |
| --- | ---: | ---: |
| 严格筛选的高质量真实 | 60% | 46.0% |
| 合成 | 36% | — |
| 文字渲染的图像 | 4% | — |
| 特定领域数据（机器人 / 驾驶 / 第一视角 / 人类活动） | — | 43.9% |
| Hard cases（人体运动 / 高速运动 / 精细操作） | — | 10.1% |

**该阶段数据的关键解释：** 也就是说 mid-training 不再追求单纯规模，而是每一块数据都在补一个明确的短板：合成图像（靠仔细的拒采样挑出来）补不常见的视觉概念和物体组合，文字渲染图像补图中文字可读性不足，特定领域片段补具身 AI 和操作场景，hard cases 补边缘情况的鲁棒性。

- 筛选手段上，真实图像要同时过「按纵横比划定的分辨率阈值」和严格的 DOVER 美学分，视频同样是更严的分辨率与美学过滤；长尾问题则靠在困难概念上加重采样概率来缓解。不过这些规则论文只给了定性表述（strict cutoff、per-aspect-ratio thresholds），没公布任何具体阈值；即训练采样看到的有效比例，怎么定出来的没有解释。


② 五类合成数据，用来补真实数据里的长尾场景，全部开源：

| 数据集 | clips | 分辨率 / FPS | 内容 |
| --- | ---: | --- | --- |
| SDG-PhyxSim | 76,489 | 1920×1080 / 30 | 物理交互场景：刚体碰撞、关节物体、形变材料、流体、光学现象 |
| SDG-RobotSim | 208,022 | 不定 | 具身机器人场景：6–8 种 embodiment 的操作与移动 |
| SDG-DriveSim | 264,000 | 3840×2160 / 24 | 自动驾驶场景：常规及长尾驾驶场景 |
| SDG-SynHuman | 236,937 | 1920×1080 / 30 | 数字人场景：人体运动、相机运动、多人交互 |
| SDG-Warehouse | 122,952 | 1920×1080 / 30 | 仓储操作场景：仓库作业及人与叉车的安全交互 |

**一些工程细节可以保证合成场景的可复现性：** PhyxSim 的可复现性做得很干净：Isaac Sim + PhysX，每帧 16 个 substep，每个 clip 用 (scene_name, scene_hash, seed) 三元组做 key，seed 决定所有随机化参数，任何一条 clip 都能从场景文件精确重放。

**有效性的验证在附录 C：** 合成数据确实落在预训练覆盖不到的长尾区域，且五个源混用比任何单源都稳（单源会伤到正交域）；唯一没救回来的是 Human 域，人的 sim-to-real gap 仍在。

③ Video transfer 数据，训练的是「控制信号 + 文本 → RGB 视频」这种可控生成。五种控制条件的获得方式不同：

| 控制信号 | 怎么获得 |
| --- | --- |
| Edge | Canny 在线计算 |
| Blur | 高斯 / 双边滤波在线计算 |
| Depth | Video Depth Anything 预计算 |
| Segmentation | SAMv2 预计算 |
| World-scenario map | MADS 驾驶数据自带 |

普通 transfer 从预训练池筛 3M 高质量视频（重点关注高质量视频以及机器人和自动驾驶等 Physical AI 域）；world-map 那一路用 MADS 的 1.1M 样本、7 路同步相机、30 FPS，自带车道线、路沿、红绿灯和动态 3D 框。

### 2.3 Post-training 阶段数据

这一阶段是按模态各自独立做的，每个专用数据集对应练出一个领域专家模型：Cosmos3-Super-Text2Image、Cosmos3-Super-Image2Video、Cosmos3-Nano-Policy-DROID（规模见图 8，分别是 8M / 20K / 58K）。三者与对应的 mid-train 模型架构完全相同，差别只在数据。所以数据集的特点是小而精，只留还需要进一步学习的部分。

- 图像：只用合成、文字渲染、高质量真实这三类，web 级预训练数据完全排除。
- 视频（一）：从预训练池抽样，作用是当 regularizer，防止模型过拟合到窄分布、把预训练学到的广泛视觉知识丢掉。
- 视频（二）：主体是 SFT 视频，三个来源各有分工——合成视频覆盖真实素材难拍到的视觉概念、运动类型和场景构成；人工精选真实视频由人挑选并标注，给关键视觉域提供直接的生成保真度信号；按 embedding 相似度从预训练池检索回来的真实视频，则用来确保覆盖常见失败案例。

**主要经验：** 先靠系统性评测找出生成质量的短板，再反向去捞对应数据，而不是盲目加量。


### 2.4 结构化 caption（所有阶段共用）

> 这个部分分了多个位置：具体来说动机和评测在 Sec. 3.2.1 的「Structured caption annotation」，完整设计在附录 A——A.1 是 captioner 模型，A.2 是图像 schema，A.3 是视频 schema；推理侧把用户请求转成同一套 schema 的 prompt upsampler 模板在附录 B。

**Motivation：论文明确说自由文本 caption 的毛病是「precise but incomplete**

描述可见内容是准的，但复杂场景总漏东西。改成预定义字段的 JSON 后，schema 本身逼着标注去系统性进可能的覆盖 objects、attributes、relationships 和场景级信息，recall 明显上升而 precision 不掉。标注器是两个 Qwen3-VL-8B，分别是用LoRA 微调成的图像版和视频版；不用现成 VLM 的理由是要完全控制输出结构、避免字段幻觉或缺失。

**除了Json的详细格式之外，标注上有几个技巧值得关注**

1. 为了避免忽略掉角落内容，图像用的是 quadrant-scan：不是盯着整张图写一段话，而是把图分成左上、右上、左下、右下四块再加正中间，五个区域各自独立描述，最后再合并成一条 caption，这样多主体和复杂布局就不会被一句话笼统带过。
2. 视频则是标两遍：第一遍按图像那套标静态内容，第二遍只标时序变化，把每个被跟踪的视觉属性随时间怎么变都过一遍。
3. 注意：视频 schema 不是另起一套，而是直接继承图像 schema 再往上加时序字段。图像那套装的是静态内容：主体（外观、位置、相对大小、朝向、姿态）、背景、光照、美学、摄影（构图、机位、景深、焦段）、风格媒介、画面里的文字，以及分辨率宽高比这类元数据。视频加的则是「随时间变了什么」：每个主体的 action 和 state_changes、相机的 camera_motion、带时间戳的事件表 actions[]、按时间段切开的 segments[]、段与段之间的 transitions，最后是整体的 temporal_caption 和可选的 audio_description。完整字段清单和能直接照抄的 JSON skeleton 在 A.2 和 A.3。
4. 字段里最有意思的是一组计数字段：number_of_subjects、number_of_arms、number_of_hands、number_of_fingers、number_of_legs。为什么要在 caption 里专门写清楚有几只手、几根手指？因为生成模型最常犯的恰恰是这类错。可见 schema 的字段不是拍脑袋列的，而是照着模型的实际失败模式反推出来的。
5. schema 里还留了 comprehensive_t2i_caption（图像）和 temporal_caption（视频）两个字段，装的不是某个属性，而是一整段自然语言——照着前面已经填好的所有字段写出来的完整描述。也就是说结构化 JSON 是中间产物：先用字段清单逼标注把该看的都看一遍，再把这些字段整合成一段话，训练时喂给模型的仍然是这段自然语言。这样做的好处是既拿到了 schema 带来的高 recall，输入形式又和用户推理时真正会打的那种一句话 prompt 对得上。


### 2.5 音频数据

网络视频中的声音，不一定真由画面中的事件产生。例如画外解说、后期配音、BGM虽然和视频一起出现，但与画面动作并没有直接时间或物理对应。所以两个阶段的目标是分开的：

Pre-training 追求：

$$\text{声音类型丰富}$$

Mid-training 追求：

$$\text{声音与可见事件在时间和因果上匹配}$$

也就是让模型学到：

$$\text{碰撞画面} \leftrightarrow \text{撞击声}, \qquad \text{嘴部运动} \leftrightarrow \text{同步语音}$$

而不是简单把网络视频的原始音轨全部当成正确监督。

**1. Pre-training：声音类型覆盖。** 直接复用预训练视频池，其中 138.9M clip 有可用音轨，涵盖 diegetic / non-diegetic 语音、旁白、BGM、环境声、音乐、物理事件；短于 30 秒的 62.5M 条用 Qwen3-Omni-Captioner 生成合成音频描述。

**2. Mid-training：音画因果对齐。** 从预训练池严格筛选到：

$$18.8\mathrm{M} = 12.8\mathrm{M}\ \text{非语音 clip} + 6\mathrm{M}\ \text{同步语音 clip}$$

基本原则是：

$$\text{只保留看得见说话人的语音} + \text{删除画外音} + \text{删除无关 BGM}$$

具体流程：

1. SAM-Audio：把音频分成 speech stem 和 remaining stem；
2. SyncNet：检测人脸与口型同步，只有置信度 $\geq 3.0$ 才算画面内语音；
3. FireRedASR2S：估计 speech ratio 和 music ratio；
4. Qwen3-VL：判断音乐是否由画面中的乐器产生——乐器演奏是要保护的，不能和无关 BGM 一起删掉；
5. 对非语音数据去除人声，对无关 BGM 进行分离，并过滤接近静音的样本；
6. 如果音轨经过处理，就重新生成 caption，避免文字继续描述已删除的声音。

同步语音那一支还要多走一步：

$$\text{Qwen3-ASR 转录语音} \rightarrow \text{GPT-OSS-120B 合并语音和环境声描述}$$

让最终 caption 同时写清说了什么、周围有什么环境声。


### 2.6 Action 数据

> 为什么仅用视频不够，以及如何加入与视频时间同步的 action 数据，把视频生成器变成 World-Action Model？

只看视频，模型学到的是「接下来大概会怎么动」，但学不到**可控生成**——同一个初始观测，在不同机器人指令、不同相机轨迹、不同车辆路线下会演化成完全不同的未来。加入 text-video-action 配对数据后，模型才能同时学会正向（给 action 预测未来）、反向（看轨迹反推 action）和联合生成。

最终规模：**8.4M episodes / 61.3K 小时**，主要分为四大块：

| 支柱 | 时长 | 占比 | 数据怎么来的 |
| --- | ---: | ---: | --- |
| 第一人称运动 | 41.3K h | 67.4% | 自有数据集，头戴 RGB 相机拍双手操作，1.7M episodes；每帧标同步的头部相机位姿 + 每只手 21 个关键点的 3D pose（含逐关节位置和朝向），所以能同时学 ego-motion 和精细手部动作 |
| 自动驾驶 | 10.0K h | 16.3% | 自有 NVIDIA Hyperion 平台驾驶日志；从大规模语料里**按目标分布挖**，刻意覆盖不同天气、光照、路况和各种纵横向机动，而不是清一色的直线巡航；轨迹从车体坐标系转到 front-wide 相机坐标系以对齐其他域 |
| 机器人 | 5.4K h | 8.7% | 开源数据集聚合，90.4K 任务 / 516.7K episodes：AgiBot（239.4K episodes / 4.37K h）、Franka Panda、Google Robot、WidowX-250、UMI、UR |
| 相机运动 | 4.6K h | 7.5% | 从预训练视频里挖，用 ViPE + DepthAnything3 估相机位姿，严格剔掉抖动过大和内参异常的片段，保持 metric scale 并转到统一坐标约定，最终得 1.9M clip |


**不同Action最后怎么统一？**
把不同action数值拉到相近尺度，避免模型只关注数值大的动作维度。
- 统一 tokenization 之后还要做幅度对齐：按维度从训练数据里统计 normalizer，把各 action 通道缩放到大致 $[-1, 1]$，否则不同 embodiment 的动作量级差太多。（这也解释了为什么 mid-training 里 action loss 要乘 $10\times$——归一化后的 action 逐元素 MSE 本来就小。）
