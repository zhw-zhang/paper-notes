## 研究问题

作者主要就是表达了3个体会：

1. Dyna-2 做到了百万小时级的人类第一视角视频训练，这个规模在机器人领域很罕见，但 1 万小时能跑的工程方案到了 100 万小时基本都开始失效
2. 机器人训练的数据形态和普通大模型不一样：
    - 一个 episode 里有多路 camera、proprioception、action，而且采样频率不同，训练时还要按时间对齐
    - 机器人模型为了端侧部署通常不会无限做大，所以模型本身可能吃数据很快，反而 dataloader / I/O 先成瓶颈
3. 当数据 scaling 到 1M，不是单纯加 GPU 就能解决的。真正的问题是瓶颈会不断转移：存储格式→数据处理→manifest→I/O→训练通信→容错 （正如作者所说：他们过去一年很多时候不是“没 idea”，而是实验等数据等太久了；单纯加 GPU 或 CPU worker 也解决不了。）


所以，Dyna-2 的百万小时训练首先是一个系统工程问题：随着数据规模从 10K h 扩到 1M h，瓶颈会在整条 data-to-training pipeline 中不断迁移，因此必须逐层重构基础设施，而不是简单堆计算资源。
然后后面整篇就是按这个逻辑，一个瓶颈一个瓶颈解决：

$$
\boxed{
\begin{gathered}
\text{Storage} \rightarrow \text{Ingestion} \rightarrow \text{Curation} \rightarrow \text{Delivery} \rightarrow \text{Training} \rightarrow \text{Resilience} \\
\text{存储} \rightarrow \text{数据处理} \rightarrow \text{manifest} \rightarrow \text{数据传输} \rightarrow \text{训练} \rightarrow \text{容错}
\end{gathered}
}
$$

## 核心方法

六个环节的「痛点 → 改法 → 收益」基本概述如下：

1. **存储：** H5 + JPEG → MCAP + H.264 + topic-group chunking。体积减少 **68%**，读取快 **2.9×**。
2. **Ingestion：** 单个大任务 → Airflow DAG + 均衡调度。吞吐从 **14k 提升到 440k episode-hours/week**。
3. **Manifest：** 遍历数千万文件 → warehouse SQL + mmap。构建时间从约 **48 小时降到 1 分钟以内**。
4. **数据传输：** 远程读取 → 节点 NVMe cache。吞吐约 **2 GB/s/node**，GPU 利用率约 **98%**。
5. **训练通信：** 全局 sharding → node-local sharding。大规模 optimizer step 约快 **3×**。
6. **容错：** preflight 检查 + checkpoint 自动恢复，让持续数周的训练不再依赖人工重启。


### 1. Episode container：MCAP + larger GOP + topic-group chunking

> 背景需求：Dyna‑2 需要同时预测视频与动作，每一条训练样本需要少量解码后的视频帧，同时需要一段长得多的本体状态序列，该序列长度与Action Chunking的尺寸匹配。另外这里有个关键需求就是：希望对任意时间戳做随机访问的需求

这种需求下带GOP的H.264肯定不行了，因为这种视频压缩机制需要从头解码速度极慢。而原来使用的 H5 + per-frame JPEG，简单是简单，但规模一大有两个问题：

- 每一帧都是独立 JPEG，没有利用相邻视频帧之间的大量冗余，存储成本很高；
- H5 本身也不方便直接预览，想检查一条数据还得先转格式。

当规模扩大，我们需要一套同时兼顾**存储、效率、便于调试查看**的存储格式。所以他们换成了广泛应用于自动驾驶领域的MCAP，其随机访问能力与灵活的分块机制尤为突出，并且这篇论文针对 WAM 所需求的video-action的读取方式做了两层优化：
1. H.264 + larger GOP 负责减少体积
2. topic-group chunking 负责减少无效读取



**Q1: MCAP 是什么？** 
- 可以把它理解成机器人数据的“多模态日志容器”，而不是一种视频编码。一个文件里可以同时放多路 camera、state、action 等不同频率的数据流：每一路是一个 topic/channel，每条 message 都带时间戳，还可以把 schema 和 metadata 一起保存。MCAP 再通过 chunk 和 index，让读取器按时间、按 topic 定位数据，不必从头扫描整个文件。

- 所以这里要区分两个层次：**H.264 负责“视频帧怎么压缩”，MCAP 负责“不同模态的数据怎么组织、索引和读取”。** Dyna 真正进一步改造的是 MCAP 内部不同 topic 如何组成 chunk。

**Q2: 为什么 WAM 可以用更大的 GOP？**

- GOP 可以简单理解成：一段视频只存一张完整的 keyframe，后面的帧主要存“相对前面变了什么”。GOP 越大，压缩率通常越高；代价是随机跳到中间某一帧时，必须先找到前面的 keyframe，再一路解码过来。

- 这对只取几个稀疏帧的 VLA 不一定划算，因为每个 sample都会随机的找起始点并且解码。但 **WAM 本来就要连续读取一段较长的视频**，因此从 keyframe 开始解码一次以后，后面很多帧都能复用，larger GOP本身就不是问题了。


> [!NOTE]
> 这里很有意思，需要注意一下：存储格式不是一个独立于模型的 infra 选择，而是和 training sample 怎么读数据绑定的。模型从“短、稀疏窗口”变成“长、连续窗口”，最合适的编码方式也会跟着变。


**Q3: topic-group chunking 到底解决什么？**

这里最容易卡住的点是：**反正训练既要 video，也要 state/action，为什么混在一个 chunk 里还会浪费？**

关键在于：它们需要读取的“密度”完全不同。

先分清三个概念：

- **topic：** 一路数据，例如 camera_1、joint_state、action；
- **message：** 某个 topic 在某个时间点产生的一条数据；
- **chunk：** 磁盘上的实际打包和读取单位。想拿其中一条 message，通常需要把整个 chunk 拉取并解压。

假设一个两秒的训练 sample 只需要：

- camera：取 4 张画面；
- state/action：按 100 Hz 连续读取，共 200 个时间点。

如图2所示。默认 MCAP 按时间把所有 topic 混合写入：

```
Chunk 1：
camera frame → state → action → state → action → camera frame → ...
```

为了拿到连续的 200 个 state/action，训练程序必须把覆盖这两秒的所有 chunk 都读进来。问题是这些 chunk 里面还塞着大量 camera frames——即使训练只需要其中 4 张，也被迫把其余视频数据一起读回来。

这就是 read amplification：**想读一点小数据，却连带读取了大量暂时不用的数据。**

topic-group chunking 改成：

```
Camera group：
[camera_1、camera_2、camera_3 ...]

State/Action group：
[proprioception、joint_state、action ...]
```

训练时就可以：

```
连续 state/action 窗口 → 只读取 State/Action chunks
少量 video frames       → 只读取相关 Camera chunks
```

因此它的核心不是“把每个 topic 单独存”，而是：

> **把读取方式相同、通常会一起使用的 topic，放进同一组 chunk。**


> [!NOTE]
> 一句话总结：**默认 MCAP 是「同一时间的数据放在一起」；Dyna 改成了「训练时会一起读取的数据放在一起」。**


![topic-group chunking：按读模式分组后一个 sample 只需 2 次读取](media/dyna-2-infra/figure2-topic-group.png "图 2｜论文 Figure 2：默认 MCAP 会把每个 topic 的整段窗口依次写入，所以一个训练 sample 要按 topic 各读一次。我们改为把读模式相同的 topic 分组——相机和相机一组、state 和 state 一组——每组按时间主序写入。这样无论组内有多少 topic，一个 sample 只需两次读取、每组一次。图中用四个 topic、两种采样率示意；真实 episode 两边都更多，所以后面测到的收益更大。来源：Dyna Robotics, https://www.dyna.co/research/dyna-2-infrastructure。"){.scale85}


### 2. Ingestion：Airflow DAG + staggered starts + bin-packing

> 背景需求：raw episode 还不能直接拿来训练。它需要经过时间对齐、质量检查、统一编码和 caption / segmentation 等特征生成，最终变成 training-ready episode。步骤本身不新鲜，真正困难的是让几百万个 episode 稳定、持续地跑完。

整条 ingestion pipeline 可以先简单记成：

```
raw episode
    ↓
transform：时间对齐、派生信号、编码成统一 MCAP
    ↓
quality check：过滤黑屏、坏帧、关节状态跳变
    ↓
feature enrichment：label、caption、segmentation
    ↓
training-ready episode
```

**Q1: 为什么一个大的 Kubernetes job 不够用？**

因为三个步骤需要的资源完全不一样。比如：

- transform 主要吃 CPU、memory 和 I/O；
- 一些 quality check 只需要 CPU；
- caption 或 segmentation 可能需要 GPU。

如果全部塞进一个 Kubernetes job，就只能按照最贵的步骤准备整套 worker。一个非关键的 caption step 挂了，也可能让前面已经完成的 transform 和 quality check 一起重跑。

换成 Airflow DAG 后，每一步可以单独申请资源，也可以单独 retry：

```
transform ✓ → quality check ✓ → caption ✗
                                  ↓ retry
                             只重跑 caption
```

它还可以通过 run profile 选择这次到底跑什么：完整处理、只补 metadata，或者重新打 label，不需要为每种需求再写一套 pipeline。

另外，每个 episode 都会留下三类 version stamp：schema version、ingestion pipeline version、采集时的 robot software version。因为 1M 小时数据不可能每次全部重刷，数据集长期 mixed-version 是正常状态；有 stamp 才知道哪些 episode 真的过期，只重做那一部分。

**Q2: 已经拆成 DAG 了，为什么继续加 worker 还是不能线性加速？**

因为 DAG 只解决了“怎么拆任务”，没有自动解决“几百万个任务怎么一起调度”。规模上来以后又出现两堵墙。

第一堵墙是 scheduler DB 的写入尖峰。假设 100 个 batch 同时启动，它们的 transform 也会差不多同时完成，于是同一秒有大量任务一起向 scheduler DB 写状态：

```
Batch 1 ── transform 完成 ┐
Batch 2 ── transform 完成 ├─→ 同一时刻集中写 scheduler DB
Batch 3 ── transform 完成 ┘
```

worker 还没吃满，scheduler 自己先被写爆了。staggered starts 的做法就是把 batch 的开始时间错开：

```
Batch 1 ── transform 完成 ──→ write
Batch 2     ── transform 完成 ──→ write
Batch 3         ── transform 完成 ──→ write
```

它没有减少任务总量，只是把瞬间的写入洪峰摊平。

**Q3: bin-packing by bytes 又解决什么？**

第二堵墙是 episode 大小差异很大。假设三个 worker 各拿一个 episode：

```
Worker A：1 GB  → 很快结束
Worker B：1 GB  → 很快结束
Worker C：10 GB → 另外两个 worker 一直等它
```

如果只按“episode 个数”平均分，看起来每个 worker 都拿了一个任务，实际负载完全不均。bin-packing 会按总字节数重新组合，并把大输入进一步切成 chunk，让每个 worker 最终处理接近的数据量：

```
Worker A：≈ 4 GB
Worker B：≈ 4 GB
Worker C：≈ 4 GB
```

> [!NOTE]
> 一句话总结：**Airflow DAG 解决“任务如何拆开和恢复”，staggered starts 解决“不要同时冲击 scheduler”，bin-packing 解决“不要有人做完了、有人还在搬大文件”。**

这些改造和前面的存储优化合在一起，把 ingestion throughput 从 **14k 提升到 440k episode-hours/week，约 31×**；处理 1M 小时从约 16 个月降到 3 周以内。这里是多项优化的整体收益，文章没有给每一项单独做 ablation。

### 3. Curation：warehouse query + mmap manifest

> 背景需求：数据都处理好了，还不能立刻训练。每次 experiment 都要先决定“这次到底用哪些 episode、每条从哪里开始、如何分给不同 GPU”，并把结果写成 training manifest。这一步直接决定一个实验是马上启动，还是先等两天。

**Q1: manifest 到底是什么？为什么每个实验都要重新生成？**

可以把 manifest 理解成这次训练的“数据目录 + 切分说明”：

```
episode_001 → 00:10 ~ 00:35 → rank 0
episode_002 → 00:00 ~ 00:18 → rank 1
episode_003 → 01:20 ~ 01:55 → rank 2
...
```

batching、GPU sharding 和 epoch length 都依赖它。不同实验又会按 task、robot、success flag、camera 是否掉线等条件筛选数据，所以不能永远复用同一份 manifest。

**Q2: 为什么构建一份 manifest 会花 48 小时？**

旧方法虽然能从 metadata DB 拿到 candidate paths，但一个 path 还不是完整的 manifest。每条 episode 还要继续访问远程存储：

```
拿到 path
   ↓
确认文件真的存在
   ↓
读取 sidecar 的 quality flag
   ↓
读取 header 的时间范围
   ↓
再打开一次，统计里面有多少 steps
```

1M 小时大约有 4300 万个 episodes，每条都做多次 remote lookup，时间自然从分钟变成了约 48 小时。

关键问题不是“数据库不够快”，而是用错了 workload。production DB 在采集、标注链路上，需要频繁写入并保证事务完整性；它不适合每次训练都横扫几千万行。

Dyna 把两种需求拆成两个系统：

- **Production DB：** 负责数据写入、采集、标注和完整性；
- **Analytical warehouse：** 通过 near-real-time CDC 同步，专门负责跨全表扫描和实验筛选。

于是 curation 变成一条 SQL：

```sql
SELECT episode_id, start_time, end_time
FROM episodes
WHERE task = ...
  AND success = true
  AND camera_ok = true
```

SQL 的结果再写成 columnar file。构建 manifest 从约 **48 小时降到 1 分钟以内**。更重要的是：以前成本来自几千万次 remote lookup，现在变成一次面向列的 table scan。

**Q3: manifest 已经建好了，为什么“加载”它仍然会把训练搞挂？**

因为“构建 manifest”和“每个 rank 加载 manifest”是两件不同的事。

第一，columnar file 放在 network mount 上时，读取过程会先看 footer，再做很多 scattered seek。每次小 seek 都变成一次远程请求，对 network mount 很不友好。

第二，如果每个 rank 都先把整张表读进内存，再取自己的 $1/N$，过程实际上是：

```
Rank 0：加载整张表 → 再切自己的 1/N
Rank 1：加载整张表 → 再切自己的 1/N
Rank 2：加载整张表 → 再切自己的 1/N
...
```

假设有 8 个 rank，整张表就可能被重复 materialize 8 次。即使最终每个 rank 只用 $1/8$，内存峰值也已经发生了。

**Q4: download once + mmap + shard-on-load 为什么必须一起用？**

最终方案分三步：

```
Object Storage
      ↓ 只下载一次
Node-local disk 上的 columnar manifest
      ↓ mmap，不整表读入 RAM
Rank 0 → zero-copy 取第 0/N 行
Rank 1 → zero-copy 取第 1/N 行
Rank 2 → zero-copy 取第 2/N 行
...
```

- **Download once：** 一个 rank 用 object storage API 把文件顺序拉到本地盘，绕过 network mount；
- **mmap：** 文件仍在磁盘，只有真正访问的 page 才进入内存；
- **shard on load：** 每个 rank 只触碰自己的 $1/N$ 行，而且是 zero-copy slice。

这里最容易误解的是：**必须先 mmap，再 shard 才有意义。** 如果先把整表读入内存，之后再切 $1/N$ 已经晚了，因为最危险的内存峰值发生在切分之前。

> [!NOTE]
> 一句话总结：**warehouse SQL 解决“manifest 怎么快速生成”；download once + mmap + shard-on-load 解决“生成以后，怎么让所有 rank 不重复搬运和加载整张表”。**

这一节把 time-to-first-batch 从“文件系统 crawl 两天”变成“SQL 几秒 + mmap 几秒”。对研究迭代来说，这往往比单步训练再快 10% 更值钱。

### 4. Delivery：用节点 NVMe 做 cluster-local cache

> 背景需求：manifest 已经告诉我们要读哪些数据，下一步是真正把这些数据送到 GPU。问题在于语料放在 cloud object storage，GPU cluster 却可能来自不同 vendor，离 bucket 很远，存储系统也完全不同。

**Q1: 为什么不把 PB 级语料直接复制到每个 cluster？**

因为它不是“复制一次就结束”：

- ingestion 还在不断增加和修正数据，每份副本都要持续同步；
- 每个 cluster 都要付 storage 和 egress；
- 不同 vendor 提供的是 Weka、VAST 或别的并行文件系统，不一定有配套 object storage。

所以他们选择：**语料只保留一份，compute 到处跑；每次训练只把本次 working set 缓存到 cluster。**

**Q2: cluster-local cache 是怎么工作的？**

训练启动前，data orchestration service 先读取 manifest，知道这次 job 会碰哪些数据，然后把它们 warm 到 GPU node 自带的 NVMe：

```
Cloud Object Storage
        ↓ 按 manifest 预热 working set
Cluster 内各节点 NVMe cache
        ↓ 本地读取
GPU training

cache miss → 再回 cloud 取
```

这样训练过程不再持续暴露在远程网络的 latency、packet loss 和 vendor 差异下面。

**Q3: 为什么要做 page-level cache，而不是把整个 episode file 缓存下来？**

假设一个 episode 文件有 10 GB，但某个 sample 只会读取其中 200 MB：

```
Whole-file cache：读 200 MB → 缓存整个 10 GB 文件
Page-level cache：读 200 MB → 只缓存真正访问的 pages
```

这里的数字只是为了帮助理解。关键点是：机器人 episode 往往很大，但一次 sample 只读其中一小段。page-level cache 可以让同样大小的 NVMe 覆盖更多 episode，淘汰时也只丢 page，不需要把整个大文件一起踢掉。

前面的 topic-group chunking 在这里又赚了一次：一个 sample 碰到的无关 chunk 越少，需要进入 cache 的 page 也越少。

**Q4: consistent hash 分配 ownership 又解决什么？**

如果每个 worker 都随意缓存文件，很容易出现热门 episode 全落在同一台节点。Alluxio 根据 path 做 consistent hash：

```
/episode/001 → Node A
/episode/002 → Node C
/episode/003 → Node B
/episode/004 → Node A
```

同一个 path 会稳定映射到同一个 worker；当文件数量达到几千万时，数据和读取流量会自然摊到整个 cluster。

> [!NOTE]
> 一句话总结：**不是把 PB 语料复制到每个 cluster，而是根据 manifest，把这次训练真正要用的 pages 提前搬到 GPU 旁边。**

远程 object storage 的单 reader 大约维持 **200 MB/s**，本地 cache 大约达到 **2 GB/s/node**，约 10×；warm multi-node run 的 GPU utilization 可以保持在 **98%**。这里最重要的不只是更快，而是不同 cluster 上的读取速度变得可预测。

### 5. Training：topology-aware optimizer sharding

> 背景需求：数据已经喂到 GPU，瓶颈又移动到了训练内部。Dyna 发现 Muon optimizer 一度占到大约一半的 step wall-clock，所以需要重新设计 optimizer state 怎么分片和通信。

**Q1: global sharding 为什么在小规模快，节点一多反而变慢？**

global sharding 的思路很自然。假设一共有 $N$ 个 rank，每个 rank 只更新第 $N$ 个参数，最后再把结果同步回来：

```
Rank 0 → 更新参数 0, N, 2N, ...
Rank 1 → 更新参数 1, N+1, 2N+1, ...
Rank 2 → 更新参数 2, N+2, 2N+2, ...
              ↓
         all-reduce / broadcast
```

节点少时，每个 rank 少算很多，通信量也不大，因此非常划算。节点一多，通信开始跨越两种速度完全不同的网络：

- **Intra-node：** 同一节点的 GPU 走 NVLink，B200 上约 **1.8 TB/s/GPU**；
- **Inter-node：** 不同节点走 InfiniBand，每张 GPU 的带宽低一个数量级以上。

global sharding 没有区分这两个层级。节点越多，越多 optimizer traffic 被迫穿过慢得多的 inter-node fabric，最后“省下的计算”反而抵不过“新增的通信”。

**Q2: node-local sharding 是怎么解决的？**

Dyna 借鉴 FSDP Hybrid Sharding，只在单个 node 内部分片：

```
Node A：[GPU 0 | GPU 1 | GPU 2 | GPU 3]
          └──── node 内通过 NVLink shard ────┘

Node B：[GPU 0 | GPU 1 | GPU 2 | GPU 3]
          └──── node 内通过 NVLink shard ────┘

Node A 与 Node B：各自重复计算同一份 optimizer update
                  不交换 optimizer traffic
```

这看起来浪费：不同 node 明明在算同一件事。可是当 inter-node communication 比 arithmetic 贵很多时，**重复计算反而比跨节点搬数据便宜。** 而且通信量被限制在单个 node 内，不再随着 node count 一直增长。

这个策略也不是任何规模都更好，所以 trainer 会根据 node count 动态选择：

```
小任务 → global sharding，少算更重要
大任务 → node-local sharding，少通信更重要
```

**Q3: 为什么作者强调看 mean，而不是 median？**

假设四个 optimizer step 的耗时是：

```
1s, 1s, 1s, 5s
```

median 看起来接近 1 秒，好像挺快；但训练真正付出的总时间是 8 秒，那个 5 秒的慢 step 没有消失。同步训练里，一个 rank 慢，其他 rank 全部要等，因此 tail latency 会被所有 GPU 一起支付。

原方案的 median 看起来还能接受，但 mean 达到 median 的 2.6×，说明慢 step 很重。大规模任务切到 node-local sharding 后，optimizer step 平均约快 **3×**。

> [!NOTE]
> 一句话总结：**小规模时“少算一点”更值钱；大规模时“少跨节点通信”更值钱。Dyna 宁可让每个 node 重复计算，也不让 optimizer traffic 穿过慢得多的 inter-node fabric。**

### 6. Job resilience：先挡住坏节点，再自动恢复

> 背景需求：小任务挂一次，重启只损失几分钟；一个多节点任务连续跑几周时，每增加一台机器，就增加一个让所有 rank 一起停住的故障点。这里不需要记很多系统细节，只要记住“运行前挡住坏节点、运行中自动恢复、算力不够时快速扩 cluster”三层。

**Q1: 为什么最麻烦的节点不是“彻底坏掉”，而是“看起来还健康”？**

彻底坏掉反而容易发现；真正难处理的是这些半坏状态：

- GPU 表面 healthy，但已经积累大量 corrected ECC error，job 总在它上面崩；
- 一次短暂 driver 查询失败把节点 drain，之后没人恢复，机器悄悄闲置十小时；
- controller 重启后留下 stale GPU reservation，机器明明空着，scheduler 却不能分配。

这些状态不会总是触发告警，却会让所有同步训练 rank 一起等。

**Q2: preflight gating 做什么？**

在 job 真正落到节点之前，Slurm 先检查：

```
GPU inventory
error counter
kernel log
local disk
container runtime
      ↓
全部通过 → 允许 job 进入
任一失败 → 先 drain 节点
```

这里有个细节：他们使用**重启后会清零的 error counter**，而不是 lifetime total。否则一张 GPU 很久以前出过一次问题，即使已经恢复，也会因为历史累计值永远被判死刑。

**Q3: 已经运行起来以后挂了，怎么恢复？**

恢复分为两层：

```
单个 worker 异常 → 原地 restart worker

整个 job 退出 → Slurm requeue
             → 从最新 checkpoint 继续
```

每次 attempt 的 diagnostic trace 会单独保存。否则自动重启虽然把训练救回来了，却会覆盖第一次失败的证据，最后只知道“它又好了”，不知道为什么挂。

**Q4: one-click cluster deployment 为什么也算 resilience？**

因为百万小时 pre-training 会占住大量 GPU 数周，但其他人还要继续训练和评测。单个 vendor 很难一直提供足够算力，所以团队必须哪里有空闲 GPU 就去哪里。

Dyna 用同一套 Ansible playbook，加上每个 cluster 自己的 inventory：

```
通用 Ansible roles
        +
Vendor A inventory / Vendor B inventory
        ↓
scheduler、container stack、network、storage 配置
```

vendor 已经安装的部分就跳过，没有的部分自动补齐。新 cluster 从手工搭建几周，变成改配置后几天上线。

> [!NOTE]
> 一句话总结：**preflight 是在坏节点加入任务前挡住它；auto-restart 是已经出事后的止损；one-click deployment 是保证还有新的健康算力可以接上。**

如果只选最关键的一层，我会选 preflight：同步训练只有所有 rank 都健康才能前进，最好不要让坏节点进入任务，再依赖 checkpoint 去补救。

## 关键发现

这篇文章可以记成一条很实用的 checklist：**每做完一次优化，都继续问“下一步的成本到底随哪个量增长？”**

| 环节 | 原来的增长项 | 改造后的思路 |
| --- | --- | --- |
| Storage | 视频体积、无关 topic 的 read amplification | H.264 压缩 + 按读取模式组织 chunk |
| Ingestion | 并发 run 对 scheduler 的写入尖峰、文件大小不均 | stagger + 按 bytes bin-pack |
| Curation | 每个 experiment 都按 episode 做远程 lookup | warehouse SQL + columnar manifest |
| Manifest loading | 每个 rank materialize 整表 | download once + mmap + zero-copy shard |
| Delivery | 远程读取的延迟和 cluster 差异 | manifest-guided NVMe page cache |
| Optimizer | inter-node traffic 随 node count 增长 | node-local shard + 跨节点重复计算 |
| Resilience | 节点数 × 运行时间带来的故障概率 | preflight + checkpoint restart + requeue |

所以这里真正的“scaling”不是把同一个方案后面继续堆机器，而是不断把成本从一个随规模增长的量，换到一个更可控的量上。

## 我的提问

### Q1：哪些设计是机器人数据特有的，哪些可以直接迁移到普通大模型训练？

机器人味最强的是 storage：多路 camera/state/action、不同采样率、不对称窗口，以及针对 WAM 长视频读取选择 larger GOP 和 topic-group chunking。

后面大部分其实很通用：production DB / warehouse 分离、manifest mmap、node-local cache、topology-aware sharding、preflight + auto-restart。只要是 PB 级多模态数据、跨多个 cluster 训练，都很容易遇到同一类问题。
