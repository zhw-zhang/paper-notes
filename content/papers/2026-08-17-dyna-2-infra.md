## 研究问题

作者主要就是表达了3个体会：

1. Dyna-2 做到了百万小时级的人类第一视角视频训练，这个规模在机器人领域很罕见，但 1 万小时能跑的工程方案到了 100 万小时基本都开始失效
2. 机器人训练的数据形态和普通大模型不一样，需要一些特殊处理。比如：
    - 一个 episode里需要有多路 camera、proprioception、action的组合，而且采样频率不同，训练时还要按时间对齐
    - 机器人模型为了端侧部署通常不会做的特别大，所以模型本身可能吃数据很快，反而 dataloader / I/O 先成瓶颈
3. 当数据 scaling 到 1M，不是单纯加 GPU 就能解决的。真正的问题是瓶颈会不断转移：存储格式→数据处理→manifest→I/O→训练通信→容错 （正如作者所说：他们过去一年很多时候不是“没 idea”，而是实验等数据等太久了；单纯加 GPU 或 CPU worker 也解决不了。）


所以，Dyna-2 的百万小时训练首先是一个系统工程问题：随着数据规模从 10K h 扩到 1M h，瓶颈会在整条 data-to-training pipeline 中不断迁移，因此必须逐层重构基础设施，而不是简单堆计算资源。
然后后面整篇就是按这个逻辑，一个瓶颈一个瓶颈解决：

$$
\boxed{
\begin{gathered}
\text{Storage} \rightarrow \text{Ingestion} \rightarrow \text{Curation} \rightarrow \text{Delivery} \rightarrow \text{Training} \rightarrow \text{Resilience} \\
\text{存储} \rightarrow \text{数据处理} \rightarrow \text{manifest} \rightarrow \text{数据传输} \rightarrow \text{训练} \rightarrow \text{容错}
\end{gathered}
}
$$

## 核心方法

六个环节的「痛点 → 改法 → 收益」基本概述如下：

1. **存储：** H5 + JPEG → H.264 with larger GOP + MCAP + topic-group chunking。体积减少 **68%**，读取快 **2.9×**。
2. **数据处理：** 单个大任务 → Airflow DAG + 均衡调度。吞吐从 **14k 提升到 440k episode-hours/week**。
3. **Manifest：** 遍历数千万文件 → warehouse SQL + mmap。构建时间从约 **48 小时降到 1 分钟以内**。
4. **数据传输：** 远程读取 → 节点 NVMe cache。吞吐约 **2 GB/s/node**，GPU 利用率约 **98%**。
5. **训练通信：** 全局 sharding → node-local sharding。大规模 optimizer step 约快 **3×**。
6. **容错：** preflight 检查 + checkpoint 自动恢复，让持续数周的训练不再依赖人工重启。


### 1. Episode container：MCAP 与 topic-group chunking

> 背景：这个部分内容原始文章讲的有点乱，且缺少大量背景知识，因此这里通过重新查找资料后进行了重整理，和原文会有一些不match，但是会更加易懂一些。


### 1.1 为什么机器人数据需要 MCAP？(原有数据读取方式问题)

一段机器人 episode 并不是单一视频，而是多路传感器持续产生的数据：

```text
一个机器人 episode
├── 左相机视频
├── 右相机视频
├── 关节状态 / 末端位姿
└── action
```

而且不同数据的采样频率并不相同：

```text
camera:   12.000s, 12.033s, 12.066s, ...
proprio:  12.000s, 12.010s, 12.020s, ...
action:   12.000s, 12.020s, 12.040s, ...
```

如果分别存成零散文件：

```text
episode_001/
├── left.mp4
├── right.mp4
├── state.npy
└── action.npy
```

还需要额外维护「哪一帧视频 ↔ 对应哪个 robot state ↔ 对应哪个 action」的对齐关系：

```text
哪一帧视频
    ↕
对应哪个 robot state
    ↕
对应哪个 action
```

> 背景： Dyna-2 早期采用per-frame JPEG，这是历史原因继承于VLA的格式。
>
> **传统 VLA 往往只取稀疏、短窗口的视频帧，因为读取帧数据存在比较强的随机、稀疏性**，如果使用H.265的GOP方式，虽然可以存储很小，但是每次都需要从附近关键帧从头解码，整体cost越大，所以为了满足这样的随机性，采用了单帧存储的方式。（GOP 可以理解成：一段视频只存一张完整的 keyframe，后面的帧主要存「相对前面变了什么」。）
>
> 但是这种的每帧存储有以下两个缺点：
>
> - 存储cost比较大：每帧可以独立访问，但没有利用视频帧间压缩，存储和读取开销很大
> - 可视化不方便：查看 episode 前还需要转换格式。

**然而不同于VLA，针对Dyna-2这种WAM的任务，会读较长的连续视频序列。** 比如一旦从 keyframe 开始解码：

$$
I_t,\ I_{t+1},\ I_{t+2},\ \dots,\ I_{t+k}
$$

后面这一大串帧本来就都是训练需要的，所以那一次 keyframe seek/decode 的成本被很多帧一起分摊了，**larger GOP 反而不再是问题，所以可以使用H.264编码同时具有large GOP**。

但是如果只有video平铺结构，如上述所示检索起来非常麻烦。为了增强数据的组织结构，提高检索效率和不同模态对齐等工作，论文最终将每个 episode 统一保存为 MCAP。


### 1.2 MCAP container

MCAP 可以理解成一个「带目录和时间轴的多模态数据盒子」，而不是一种视频编码格式，而是一种组织形式。它把一个 episode 的多路数据统一保存在同一个文件里，并按 **topic + timestamp** 组织。下面是一个具体的例子，展示数据格式：

```
episode.mcap
├── /camera_left                              ← topic
│   ├── msg(t_pub=12.000, t_log=12.002) → frame
│   ├── msg(t_pub=12.033, t_log=12.035) → frame
│   └── ...
│
├── /camera_right                             ← topic
│   ├── msg(t_pub=12.000, t_log=12.003) → frame
│   └── ...
│
├── /proprio                                  ← topic
│   ├── msg(t_pub=12.000, t_log=12.001) → robot state
│   ├── msg(t_pub=12.010, t_log=12.011) → robot state
│   └── ...
│
└── /action                                   ← topic
    ├── msg(t_pub=12.000, t_log=12.001) → action
    ├── msg(t_pub=12.020, t_log=12.021) → action
    └── ...
```

每一路数据称为一个 **topic**，topic 内部由连续的 message 构成：

```
message
├── topic / channel   → 属于哪一路数据
├── publish_time      → 上游产生或发布消息的时间
├── log_time          → recorder 记录消息的时间
└── data              → frame / robot state / action
```

因此可以简单理解为：

```
message = topic + timestamp + data
```

时间戳来自原始采集系统和 recorder（如果没有独立的 `publish_time`，可令它等于 `log_time`）。**MCAP 只负责保存和索引时间信息，并不自动完成传感器同步**，下游再根据时间戳完成不同模态之间的对齐或重采样。


> [!NOTE]
> **上面展示的格式就是Dyna-2使用的改进后的格式了，包含： H.264 with larger GOP的格式 + MCAP快速检索，和topic-group chunking的形式；**
>
> - 默认 MCAP 是「同一时间的数据放在一起」；Dyna-2 改成了「训练时会一起读取的数据放在一起」。 下一个section介绍了两者的具体区别


### 1.3 默认MCAP之后，为什么还需要 topic-group chunking？

MCAP 内部不会逐条单独读取 message，而是把一批 message 放进一个 **chunk**，reader 再通过 index 定位。问题在于，Dyna-2 对不同模态的读取并不对称：

```
一个 Dyna-2 training sample
├── camera：只需要少量视频帧
└── state/action：需要一段更长、更密集的序列
```

MCAP 的默认 writer 会按照 log_time，把不同 topic 的 message 混合写入 shared chunks：

```
默认 MCAP
episode.mcap
├── chunk_0  [t0, t1]
│   └── camera_left + proprio + camera_right + action + ...
│
├── chunk_1  [t1, t2]
│   └── proprio + camera_left + action + camera_right + ...
└── ...
```

同一时间发生的 video 和 state 被物理地写在一起。于是，为了读取一长段 /proprio + /action，sampler 可能不得不把同一 chunk 中大量不需要的 camera 数据也取回来，产生无关 I/O。视频远比 state 大，只为拿一小段状态去打开混写 chunk，等于把沉重的 camera frames 一起拖进来。

Dyna-2 因此按照**相似的读取模式**重新组织 topic：

```
Dyna-2 topic-group chunking
episode.mcap
├── video group                          ← 组内按时间排列
│   ├── video_chunk_0 [t0, t1]
│   │   └── /camera_left + /camera_right
│   └── video_chunk_1 [t1, t2]
│       └── /camera_left + /camera_right
│
└── state/action group                   ← 组内按时间排列
    ├── state_chunk_0 [t0, t1]
    │   └── /proprio + /action
    └── state_chunk_1 [t1, t2]
        └── /proprio + /action
```

关键是：

```
camera topics 可以共享 video chunk
state/action topics 可以共享 state chunk

但是：
video group 与 state/action group 永远不共享 chunk
```
> [!NOTE]
> **Topic-group chunking 好处**： 这样既保留了组内的时间顺序，又避免不同读取模式的数据相互拖累。例如只需要高频 robot state 时，可以只 fetch 较小的 state chunks，而不必加载同一时间段里大得多的 video chunks (原图2是论文对这方面的解释，感觉不是很易懂，和我上面说的差不多。。)

### 1.4 训练时如何检索？三者关系如何？

```
指定 topics + 时间范围
          ↓
判断它们属于哪个 topic group
          ↓
MCAP index 定位对应时间段的 chunks
          ↓
只 fetch 真正需要的 video/state chunks
          ↓
读取 message，并按时间戳组成 sample
```

因此，检索加速来自两层：

```
MCAP index
└── 更快定位目标 topic / 时间段所在的 chunk

topic-group chunking
└── 定位以后，避免读取同一 chunk 中的大量无关模态
```

在真实 teleoperation episode 上，Dyna-2 报告：

```
H.264 compression
└── 相比 per-frame JPEG，存储减少约 68%

topic-group chunking
├── 每个 sample 的 chunk fetch 数减少约 3.4×
└── 实际读取速度提升约 2.9×
```

两者是相互独立的：**H.264 减少数据大小；topic-group chunking 改变 message 的存放顺序，主要减少无关 I/O，并不会进一步压缩文件。**

**最后三者的关系**

```
MCAP
└── 负责：装下完整 episode
          + 组织 topics
          + 保存时间戳
          + chunk/index 随机读取

H.264
└── 负责：利用视频帧间冗余压缩 camera 数据

topic-group chunking
└── 负责：按照训练时的读取模式组织 chunks
          减少读取无关 topic 带来的 I/O
```

> [!NOTE]
> 一句话总结：**MCAP 解决「多模态 episode 怎么统一保存和按时间检索」，H.264 解决「视频怎么压得更小」，topic-group chunking 解决「训练时怎么只读取真正需要的数据，减少无关I/O」。**
>
> 相比 per-frame JPEG，存储减少约 68%；相比默认MCAP，实际读取速度提升约 2.9×


![压缩与 topic-group chunking 的正交收益：体积、读延迟、chunk fetch](media/dyna-2-infra/figure3-storage-chunking.png "图 3｜论文 Figure 3：压缩和 chunking 带来的存储体积下降与读取性能提升。两者正交：chunking 改的是 message 写入顺序，不改体积，所以第 1 栏与 MCAP+H.264（per-topic）相同（均为 25.1 MB/camera-minute）；收益体现在第 2 栏读延迟（27.0 → 9.4 ms）和第 3 栏 chunk fetch 次数（11.33 → 3.29）。来源：Dyna Robotics"){.scale85}

### 2. Ingestion：Airflow DAG + staggered starts + bin-packing

> 背景：raw episode 还不能直接用于训练。它需要先完成多模态时间对齐、质量检查、统一编码，以及 caption / segmentation 等特征生成，才能变成 training-ready episode。Dyna-2 原来的 ingestion pipeline 上限只有 **14,000 episode-hours/week**；按这个速度，处理 1M 小时需要一年以上。


### 2.1 Ingestion 到底在处理什么？

原文先把典型的机器人数据 ingestion 分为三个阶段：**data transformation、quality check 和 feature enrichment**。

```
raw episode
    ↓
1. data transformation
    ↓
2. quality check
    ↓
3. feature enrichment
    ↓
training-ready episode
```

**1. Data transformation：把不同来源的数据整理成统一格式**

一条 episode 里的 camera、proprioception 和 action 原本有各自的采样频率与时间戳。Transformation 会完成：

- 把 camera 和 proprioception 重采样到统一的 timestamp grid；
- 计算训练需要的 derived signals；
- 把视频编码进统一的 canonical MCAP；
- 为结果建立 metadata index，方便后面的 manifest query。

可以简单理解成：

```
原始多路传感器流
├── camera：频率 A、时间戳 A
├── proprio：频率 B、时间戳 B
└── action：频率 C、时间戳 C
          ↓ transform
统一时间轴 + 统一 MCAP + 可查询 metadata
```

**2. Quality check：找出不能用于训练的脏数据**

例如 camera blackout、坏帧、joint state 卡顿或跳变、手部位置缺失 / 被遮挡等。它解决的是「数据虽然成功上传了，但内容是否真的可用」。

**3. Feature enrichment：补上训练需要的派生信息**

例如 performance label、video caption、segmentation，以及其他训练特征。

> [!NOTE]
> 这三个步骤本身并不新鲜。真正的 challenge 是：**如何让几百万个 episode 连续跑很多天，既不浪费 CPU / GPU，又能在局部失败后接着跑，而不是从头重来。**


### 2.2 为什么单个 Kubernetes job 会失效？

Dyna-2 早期把整条 processing pipeline 放进一个 Kubernetes job。可以把它想成一个很大的黑盒：

```
一个 Kubernetes job
└── transform → quality check → feature enrichment
```

这样做在数据较少时很直接，但规模变大后有三个问题：

- 每一步需要的资源不同，却被绑在同一套 worker 配置里；
- 中间过程不容易观察和恢复，局部失败可能拖垮整次处理；
- vendor、数据格式和处理需求一直变化，单体脚本很容易越写越多分支。

因此，他们把 pipeline 重写成 Airflow DAG，把每个处理步骤显式拆成一个 node。原文按照下面的顺序总结了三个收益。

**收益 1：Separate scalability，每一步独立扩缩容**

不同步骤的资源需求差异很大：

```
transform             → CPU + memory + I/O 较重
部分 quality check    → 主要需要 CPU
caption / segmentation → 可能需要 GPU
```

单体 job 往往只能按最贵步骤的资源上限配置整个 worker pool；即使当前只在做轻量 QC，昂贵的 GPU 或大内存也可能闲着。拆成 DAG 后，每个 step 可以动态申请与自己匹配的 CPU、memory 或 GPU，因此不是「整条 pipeline 一起扩」，而是「瓶颈在哪一步，就只扩哪一步」。

**收益 2：Better decoupling and observability，局部失败只恢复局部**

每个 step 都可以标记为 critical 或 non-critical，状态也直接显示在 DAG 上：

```
transform ✓ → quality check ✓ → caption ✗（non-critical）
                                      ↓ retry
                                 只重跑 caption
```

一个非关键 enrichment step 失败，不必取消整条 DAG；已经完成的 transform 和 quality check 也不用重做。真正关键的步骤失败时，系统可以明确停在失败位置，而不是只知道「这个大 job 又挂了」。

**收益 3：Dynamic orchestration，运行时选择要跑哪些步骤**

外部 vendor 的数据类型、格式和质量问题各不相同，因此处理流程不可能永远固定。DAG 允许在 runtime 打开或关闭任意一组步骤。例如 quality check 可以作为 transformation 前后的独立 gate：

```
pre-QC → transformation → post-QC → enrichment
  on          on             on          off
```

这次只想补 metadata，就关闭不相关步骤；下次只想重新打 label，也不需要改代码或再复制一套脚本。


### 2.3 DAG 之外，还需要 durable state、run profile 和 version stamp

这里核心是在区分：**DAG 只规定「怎么走」，durable state 负责记录「走到哪了」。**

```
DAG
└── 定义有哪些步骤，以及步骤之间的依赖关系

durable state
└── 把每个步骤的执行状态持久化保存到数据库 / 存储中
```

例如一个 episode 已经处理到这里：

```
格式转换      ✓
质量检查      ✓
视频 caption  进行中
```

如果状态只存在运行进程的内存中：

```
进程崩溃
    ↓
进度丢失
    ↓
整个 episode 可能需要重新处理
```

使用 durable state 后：

```
进程崩溃
    ↓
重新读取持久化状态
    ↓
知道前两步已经完成
    ↓
从 video caption 继续
```

标题中的另外两个概念是：

```
run profile
└── 决定本次运行 DAG 中的哪些步骤（根据durable state进行决策）
    ├── full processing：执行完整流程
    ├── metadata backfill：只补充 metadata
    └── re-label：只重新生成标签

version stamp
└── 记录每个 episode 是由什么版本处理出来的
    ├── schema version
    ├── pipeline version
    └── robot software version
```

重新处理 1M 小时需要数周，所以 pipeline 升级后不可能立刻刷完全部旧数据，corpus 长期 mixed-version 是正常的。version stamp 让系统能只重处理过期 episode，也能让 curation query 按版本范围筛选。

> [!NOTE]
> **一句话总结：** DAG 定义处理流程，durable state 保存执行进度，run profile 选择本次运行哪些步骤，version stamp 记录数据由哪个版本产生。


### 2.4 拆成 DAG 后，为什么增加 worker 仍不能线性提速？

DAG 只是把处理流程拆成多个可独立执行的步骤。但当数百万个任务同时运行时，又出现两个瓶颈：

```text
瓶颈 1：大量任务同时完成 → scheduler 承受瞬时压力
瓶颈 2：文件大小不同     → worker 工作量不均
```

**1. Staggered starts：错开启动时间，避免拥挤写入**

如果大量 batch 同时启动，它们通常也会在相近时间完成相同步骤，并同时向 scheduler 写入状态：

```text
同时启动
   ↓
同时完成
   ↓
集中访问 scheduler DB
   ↓
scheduler 成为瓶颈
```

Dyna-2 将不同 batch 的启动时间错开：

```text
Batch 1：现在启动
Batch 2：稍后启动
Batch 3：再晚一些启动
```

这样任务完成和状态写入也会自然错开，避免 scheduler DB 瞬间过载。

**2. Bin-packed batches：按照文件大小均衡分组**

不同 episode 的文件大小差异很大。如果只按照文件数量分配：

```text
Worker 1：10 个小文件(10M) → 很快完成
Worker 2：10 个大文件(10G) → 仍在处理
```

Dyna-2 改为按照**总字节数**进行 bin-packing，让每组数据量尽量接近，再拆成 chunks 并行处理：

```text
原始文件
    ↓
按照大小均衡分组
    ↓
每个 worker 获得接近的工作量
```

> [!NOTE]
> **一句话总结：** 这些优化最终将数据处理吞吐量从每周约 14,000 episode-hours 提升到 440,000 episode-hours（约 31×）。这意味着原本需要大约 16 个月才能处理完毕的工作，现在可以在不到三周的时间内完成。
因此，完整逻辑是：

```text
DAG
└── 解决任务拆分和管理

staggered starts
└── 避免大量任务同时冲击 scheduler

bin-packing
└── 避免不同 worker 工作量不均
```

![数据处理吞吐随时间提升：14k 见顶后改写抬到 440k](media/dyna-2-infra/figure5-ingestion-throughput.png "图 5｜论文 Figure 5：数据处理吞吐随时间的变化，纵轴是每周处理的 episode-hours。序列从 2 月的约 10k 开始；14k 是原来单 job pipeline 的天花板，正是这次改写把它抬了起来，到 6 月达到约 440k。来源：Dyna Robotics"){.scale85}


### 3. Curation：warehouse query + mmap manifest

> 背景：完成 ingestion 以后，数据只是变成了 training-ready episodes，还没有决定「这次实验具体训练哪些数据」。每个 experiment 都要重新做一次 curation，并生成对应的 training manifest。在 1M 小时规模下，Dyna-2 原来仅仅构建 manifest 就需要约 **48 小时**，也就是说 GPU 还没有看到第一批数据，实验已经先等了两天。

### 3.1 Manifest 是什么？为什么每次实验都要重新生成？

可以把 manifest 理解成一次训练的数据目录。它明确记录：

```
这次训练使用哪些 episode
每个 episode 从哪里开始、到哪里结束
每个 episode 包含多少 training steps
后续如何 batching、sharding，以及一个 epoch 有多长
```

一个简化后的 manifest 可能长这样：

```
episode_001 → path_A → 00:10 ~ 00:35 → 750 steps
episode_002 → path_B → 00:00 ~ 00:18 → 540 steps
episode_003 → path_C → 01:20 ~ 01:55 → 1050 steps
...
```

它不是整个 corpus 的固定目录，因为不同 experiment 会使用不同的筛选条件：

```
Experiment A：只要 task = folding，且 success = true
Experiment B：只要 robot = model_B，且 camera 没有掉线
Experiment C：只要新 pipeline version 处理过的数据
```

所以，每次实验都要根据 task、robot、success flag、camera quality、version stamp 等条件重新做 curation，再生成一份属于这次实验的 manifest。

```
完整 corpus
    ↓ curation：按实验条件筛选
本次实验的 episodes
    ↓ 写出
training manifest
    ↓
batching / GPU sharding / epoch length
```


### 3.2 为什么旧方法构建 manifest 需要 48 小时？

Dyna-2 最初会先从 metadata DB 得到一组 candidate paths。但一个 path 只说明「某个文件可能在那里」，还不足以直接成为 manifest 中的一行。

对于每个 episode，旧流程还要继续访问 storage：

```
metadata DB 返回 candidate path
    ↓ 第 1 次：确认文件真的存在
    ↓ 第 2 次：读取 sidecar，取得 quality flags
    ↓ 第 3 次：打开 header，取得 start / end time
    ↓ 第 4 次：再次打开文件，统计 training steps
manifest row 才完整
```

在 1M 小时的数据集中，当时大约有 **43 million episodes**。按每条 4 次 storage trip 粗略计算，就是：

$$ {.boxed}
43\text{M episodes} \times 4\text{ trips/episode} \approx 172\text{M storage trips}
$$

单次 remote lookup 也许不慢，但把它重复一亿多次，时间就从分钟累积到了约 48 小时。

```
旧方法的成本
≈ episode 数量
× 每条 episode 的 remote storage trips
× 单次访问延迟
```

对一次超大 pre-training 来说，这个代价也许还能勉强付一次；但每个 experiment 都重新付一次，会直接卡住研究迭代。


### 3.3 为什么需要 Warehouse？

> [!TIP]
> 这个地方设计很多专业名词： Production DB/Warehous、 metadata、episode等。强烈建议看一下补充知识，再回来更好理解一些。 [关键细节补充：数据库 metadata、Production DB 与 MCAP episode 的关系](#section-34)。

每个 episode 的信息原本已经保存在 Production DB中，组织形式如下：

```
episode_id | path | task | success | camera_ok | num_steps
```

但 Production DB 正在服务日常数据生产：

```
机器人上传数据        → 写入一行
标注员修改标签        → 更新一行
quality check 完成    → 更新一个状态
```

这些都是**频繁、小规模的读写操作**。

而构建当前训练用的数据集往往需要：

```
扫描几千万个 episode
        ↓
筛选满足条件的数据
        ↓
生成训练清单
```

这是一次**大规模全表查询**。如果直接查询 Production DB，可能拖慢机器人上传、标注等线上操作。

因此，Dyna 把 metadata 持续同步一份到 Warehouse：

```
Production DB
└── 服务机器人采集和标注，保证线上读写稳定
          │
          └── metadata 持续同步
                      ↓
Warehouse
└── 专门负责大规模扫描和训练数据筛选
```

Warehouse 保存的是 metadata 的查询副本，不是把所有视频再复制一遍。


### 3.4 Warehouse 如何把 manifest build 变成一条 SQL？

因为 Warehouse 中已经把构建 manifest 需要的信息整理成了表：

| episode_id | path | task | success | camera_ok | num_steps |
| --- | --- | --- | --- | --- | --- |
| 001 | ... | folding | true | true | 500 |
| 002 | ... | folding | false | true | 420 |
| 003 | ... | pick | true | true | 600 |

现在只需要通过 SQL 筛选：

```sql
SELECT episode_id, path, start_time, end_time, num_steps
FROM episodes
WHERE task = 'folding'
  AND success = true
  AND camera_ok = true
```

得到：

```
episode_001 | path | start_time | end_time | 500
```

把查询结果保存成表格文件，就是 manifest：

```
Warehouse
    ↓ SQL 筛选
满足训练条件的 episode
    ↓ 导出
manifest file
    ↓
训练程序按照清单读取对应的 MCAP
```

所以这两部分的核心关系是：

```
Production DB：记录和更新 episode 信息
Warehouse：    批量筛选 episode
Manifest：     筛选后得到的训练数据清单
```

SQL 结果随后写成一个 columnar manifest file，供训练读取：

```
过去：没有表，逐个文件查询
候选 paths → 数千万个 episode 逐文件检查 → manifest

现在：有表，那么只读少数 metadata 列，并且可以并行
warehouse table → 一条 SQL 扫描需要的 columns → manifest
```

关键变化不是简单把单次 lookup 优化得更快，而是**不再让构建成本由数千万次文件访问组成**。query planner 面对的是一张可以横向扩展的表，而不是一个需要逐个打开的 file list。

因此，完整表已经超过 **50 million rows** 时，curation query 仍然可以在几秒内返回；manifest build 从约 **48 小时降到 1 分钟以内**。

> [!NOTE]
> 到这里解决的只是第一半：**warehouse SQL 解决「manifest 怎么快速生成」**。manifest 生成以后，每个 training rank 如何读取它，是另一个独立问题。


### 3.5 Manifest 已经生成了，为什么加载仍然会把训练搞挂？

旧的 manifest loading 在 100K 小时规模还能工作，到 1M 小时时出现两个问题。

**问题 1：每个 rank 都加载完整表，CPU RAM 被重复占用**

假设 manifest 大小为 $M$，共有 $N$ 个 ranks。如果每个 rank 都先把完整 manifest materialize 到内存，再切自己的 $1/N$：

```
Rank 0：加载完整 M → 再取自己的 1/N
Rank 1：加载完整 M → 再取自己的 1/N
Rank 2：加载完整 M → 再取自己的 1/N
...
Rank N：加载完整 M → 再取自己的 1/N
```

那么切分前的总内存量级是：

$$ {.boxed}
\text{naive memory} \approx N \times M
$$

GPU node 通常有约 **2 TB CPU RAM**，但在大量 ranks 重复加载 million-hour manifest 时，依然可能超过这个上限，导致训练一步都没开始就 OOM。

**问题 2：columnar file 在 network mount 上会产生大量 scattered seeks**

先用一个类比理解：**manifest 像一本很厚的目录册，但这本书不在手边，而是在远程仓库。**

- 如果整本搬回来，只需要叫一次快递；
- 如果先要目录、再要第 10 页、然后第 200 页，仓库可能要分多次把这些页送过来。

后者即使总共只读了很少的数据，也可能因为来回次数太多而更慢。

对应到 columnar manifest，可以先把它想成下面这个表：

```
episode_id | path | start_time | end_time | num_steps
```

它在文件里通常不是一行一行连续存放，而是把相同 column 的数据放在一起，并按 row group 切成多个块：

```
manifest file
├── path column：       page 1、page 2、page 3 ...
├── start_time column： page 1、page 2、page 3 ...
├── num_steps column：  page 1、page 2、page 3 ...
└── footer：记录每个 column / row group 在文件中的位置
```

reader 要读取 path 和 num_steps 时，会先看 footer，再跳到文件中几个不连续的位置：

```
先读 footer
    ↓
跳到 path column 的 page 1
    ↓
跳到 num_steps column 的 page 1
    ↓
再跳到下一个 row group 的相关 pages
```

这里的 seek 就是「跳到文件的另一个位置继续读」，scattered seeks 就是「在很多分散位置之间反复跳转」。

```
本地磁盘
└── 文件就在机器旁边，来回跳转的延迟较小

network mount
└── 每次跳转都可能产生一次远程请求和网络往返
```

例如需要读取 100 个分散的小块时，network mount 可能要承受接近 100 次远程往返；一次把整个 manifest 顺序下载到本地，虽然传输的总 bytes 可能更多，却只需要一条连续的数据流。这里的 100 只是帮助理解的例子，不是原文测量值。

> [!NOTE]
> 所以问题不只是「远程存储带宽不够」，而是**大量小而分散的读取，让网络往返延迟不断累积**。Dyna 的第一步就是先把 manifest 一次性下载到本地，再做后续随机读取。


### 3.6 Download once + mmap + shard-on-load 为什么必须一起使用？

继续用一个具体例子：假设 manifest 是 **8 GB**，一台训练节点上有 **8 个 ranks**，最终每个 rank 只需要其中 $1/8$，也就是约 1 GB 的行。

旧方法相当于：

```
8 个 ranks
├── Rank 0：从远程零散读取完整 8 GB → 最后只保留自己的 1 GB
├── Rank 1：从远程零散读取完整 8 GB → 最后只保留自己的 1 GB
├── ...
└── Rank 7：从远程零散读取完整 8 GB → 最后只保留自己的 1 GB
```

这里同时有三层浪费：

```
远程 I/O：8 个 ranks 重复访问同一份远程文件
读取模式：每个 rank 都在 network mount 上做 scattered seeks
内存：    每个 rank 先加载 8 GB，再丢掉其中 7/8
```

最坏情况下，仅完整 materialize manifest 就可能产生约 $8 \times 8=64$ GB 的进程内存，而真正需要的数据总共只有 8 GB。这里的 8 GB 和 8 ranks 都是为了说明机制的示例，并非原文公布的实际 manifest 大小。

Dyna-2 的三个改动正好分别消掉这三层浪费：

```
Object Storage
      ↓ 1. Download once：一个 rank 连续下载一次，到本地
Node-local disk 上的 columnar manifest
      ↓ 2. mmap：8 个 ranks 映射同一份本地文件
Mapped table
      ↓ 3. shard-on-load：每个 rank 只访问自己的 1/8 rows
Rank-local shard
```

**1. Download once：先把「远程翻页」变成「本地翻页」**

由一个 rank 通过 object storage API，把 manifest 直接、并行地下载到 node-local disk：

```
过去：8 个 ranks 各自对远程文件做许多小读取
现在：1 个 rank 连续下载一次 → 8 个 ranks 读取本地文件
```

这一步解决的是**远程 I/O 和 scattered remote read**，但还没有解决每个 rank 是否会把完整 8 GB 都复制进 RAM。

**2. mmap：让文件看起来可以直接访问，但不立刻全部搬进 RAM**

mmap 可以简单理解成：给进程一张「文件地址地图」。进程可以像访问内存一样访问文件，但操作系统只在真正访问某个 page 时，才把那一页从本地磁盘加载进 RAM。

```
普通 read
└── 先把完整 8 GB 读成一个内存对象，再开始使用

mmap
└── 8 GB 文件仍留在本地磁盘
    访问哪一页，操作系统才把哪一页放进 RAM
```

可以理解为：mmap 是把书放在共享书架上++方便寻址，用到哪页再翻哪页，主要是为了shard-on-load做铺垫++；shard-on-load 是提前规定每个人只负责其中一章，只读和自己相关的部分进入各自rank的内存里面就行了。

**3. Shard-on-load：从一开始就规定每个 rank 只能看mmap中自己的部分**

系统先在 mapped table 上切分 row range，再让每个 rank 访问自己的 $1/8$：

```
Rank 0 → 只访问第 0/8 ~ 1/8 的 rows（约 1 GB）
Rank 1 → 只访问第 1/8 ~ 2/8 的 rows（约 1 GB）
Rank 2 → 只访问第 2/8 ~ 3/8 的 rows（约 1 GB）
...
Rank 7 → 只访问第 7/8 ~ 8/8 的 rows（约 1 GB）
```

这里的 zero-copy slice 不是把自己的 1 GB 再复制一份，而是在 mapped table 上创建一个只指向对应 row range 的视图。

**为什么不能先完整 read，再 shard？**

因为顺序反了：

```
错误顺序
完整 read 8 GB → 再留下自己的 1 GB
└── 7 GB 已经被白白读进内存，峰值已经发生

正确顺序
mmap 文件 → 先取得自己的 1/8 row view → 只访问对应 pages
└── 不需要先 materialize 完整 8 GB
```

因此三者不是三个重复优化，而是依次解决不同问题：

```
download once
└── 远程文件只连续下载一次，解决网络请求浪费

mmap
└── 不预先把完整文件复制进每个 rank 的 RAM，提供map方便寻址，为shard-on-load做铺垫

shard-on-load
└── 确保每个 rank 只触碰自己的 pages，而不是逐渐读完整表
```

> [!NOTE]
> **一句话总结：**
>
> - **warehouse SQL** 解决「manifest 怎么从几千万条 episode 中快速生成」；
> - **download once** 解决「不要让每个 rank 重复走远程存储」；
> - **mmap + shard-on-load** 解决「不要让每个 rank 先把完整 manifest 搬进 RAM 再切分」。

> [!TIP]
> - 最终，manifest build 从数千万次 filesystem lookup 变成几秒级 warehouse query；manifest loading 从分钟级整表读取变成几秒级 mmap (with shard-on-load)。整个 cold time-to-first-batch 从约 **48 小时降到 1 分钟以内**。
> - 通过这些改变，这些操作不再需要占用初创公司的关键资源了：生成清单的过程从需要数天的时间缩短到了仅仅一次查询即可完成，而清单的加载时间则从几分钟缩短到了几秒钟。

![百万小时 manifest 的加载时间与内存占用：mmap 相对读进内存](media/dyna-2-infra/figure7-manifest-load.png "图 7｜论文 Figure 7：百万小时训练 manifest 的加载时间和内存占用改善。读进内存：737.0 秒、每节点驻留 2151 GB；改为 memory-mapped 后：12.4 秒、218 GB。来源：Dyna Robotics"){.scale85}

### 4. Delivery：用节点 NVMe 做 cluster-local cache

> 背景需求：manifest 已经告诉我们要读哪些数据，下一步是真正把这些数据送到 GPU。
> 
> 注意区分：
```
manifest
└── 告诉训练程序要读取哪些 episode

MCAP
└── 真正保存 video、state 和 action 数据
```

### 4.1 当前遇到的问题？

**问题：数据在云端，GPU 集群离得很远。** Dyna-2 的百万小时PB级数据存放在统一的 cloud object storage 中，而 GPU 集群可能来自不同厂商、位于不同地区：

```text
Cloud Storage
└── PB 级 MCAP 数据
        |
        | 远程网络读取
        ↓
GPU Cluster
```

++不能给每个集群都复制一份完整数据，因为：++

```text
数据量太大
+ 数据还在不断更新
+ 多份存储和跨云传输成本很高
```

++但训练时直接远程读取也很慢：++

```text
GPU 需要一个 sample
    ↓
向云端请求 MCAP 数据
    ↓
等待网络往返
    ↓
数据到达 GPU
```

长达数周的训练中，网络延迟、丢包或偶发卡顿都会让 GPU 等待数据, 这是不可接受的对于大批量集群利用率来说。

### 4.2 解决：把需要的数据提前放到 NVMe

每台 GPU 节点通常自带高速 NVMe SSD。Dyna-2 把这些 NVMe 组合成一个 cluster-local cache：

```text
Cloud Storage
└── PB 级 MCAP 数据
        |
        | 根据 manifest 提前加载需要的数据
        ↓
Cluster-local cache
├── Node 1 NVMe
├── Node 2 NVMe
└── Node 3 NVMe
        ↓
GPU 训练
```

可以把它理解为：

```text
Cloud Storage = 远处的大仓库
NVMe Cache    = GPU 旁边的小仓库
Manifest      = 本次训练的提货清单
```

训练开始前，系统根据 manifest 找出本次需要的 episode，提前将相关数据缓存到集群内部。训练时优先读取 NVMe；如果缓存中没有，再回到云端读取。

```text
请求训练数据
    ↓
本地缓存中有？
    ├── 是 → 从 NVMe 高速读取
    └── 否 → 从云端读取，并放入缓存
```

### 4.3 放到NVMe的数据由Alluxio统一管理

> [!TIP]
> Alluxio 是位于 GPU 训练程序与云存储之间的分布式缓存系统。更完整的背景见文末 [2. Alluxio 是什么？](#section-35)。

Dyna-2 使用 Alluxio 将多个节点的 NVMe 组织成分布式缓存，主要做了三件事。

**1. 只缓存要读取的相关数据，而不是整个 MCAP 文件：**

```text
一个大型 episode.mcap
├── 已读取的部分 → 缓存
└── 没有读取的部分 → 不缓存
```

因此，一个 sample 只读取少量 chunks，就只会占用少量缓存空间。前面的 topic-group chunking 在这里再次发挥作用：

```text
需要 state/action
    ↓
只读取对应 chunks
    ↓
只有相关 pages 进入 NVMe cache
```

**2. 把缓存均匀分散到不同节点：**

```text
episode A 的 pages → Node 1 NVMe
episode B 的 pages → Node 2 NVMe
episode C 的 pages → Node 3 NVMe
```

Alluxio 根据文件路径做一致性哈希，决定数据由哪个节点保存，避免所有请求集中到一个节点。

**3. 最终效果**

```text
直接从云端读取：约 200 MB/s
集群 NVMe 缓存：约 2 GB/s per node
```

本地缓存大约快一个数量级，而且读取速度更加稳定。

完整流程可以总结为（也可对照下图8）：

```text
Manifest 确定本次训练数据
    ↓
提前把需要的 MCAP pages 加载到节点 NVMe
    ↓
训练优先从 cluster-local cache 读取     ┐
    ↓                                    ├─ Alluxio 统一管理调度
缓存缺失时再访问 cloud storage           ┘
    ↓
减少 GPU 等待，保持稳定训练吞吐
```

++训练优先从 cluster-local cache 读取++、++缓存缺失时再访问 cloud storage++ 这两步不是训练程序自己东查西找，而是由 **Alluxio 统一管理调度**：命中就从节点 NVMe 返回，缺失则回云端拉取并写入 cache。

> [!NOTE]
> **一句话总结：** Dyna-2 没有复制整个 PB 级数据集，而是根据 manifest，把本次训练真正会访问的 MCAP 数据提前缓存到 GPU 节点的 NVMe 上，让 GPU 尽量从「身边的高速硬盘」读取，而不是每次都去远程云端取数据。

![集群内数据编排：cloud storage、control plane 与节点 NVMe / NFS](media/dyna-2-infra/figure8-on-cluster-orchestration.png "图 8｜论文 Figure 8：on-cluster data orchestration。Control plane 根据 manifest 预热 working set，再把数据放到各集群的 NVMe cache 与 cluster NFS；cache miss 回落到 cloud storage。来源：Dyna Robotics"){.scale85}

### 5. Training：topology-aware optimizer sharding

> 背景需求：数据已经可以稳定地送到 GPU，瓶颈又移动到了训练内部。GPU 数量增加后，optimizer 更新需要在不同 GPU 之间交换大量数据，跨节点通信逐渐成为瓶颈。

### 5.1 什么是 optimizer sharding？

Dyna-2 使用 Muon optimizer。optimizer step 一度占据约一半训练时间。

为了加速，可以把参数更新任务分给不同 GPU：

```text
全部参数更新
├── GPU 0：更新第 0、4、8...组参数
├── GPU 1：更新第 1、5、9...组参数
├── GPU 2：更新第 2、6、10...组参数
└── GPU 3：更新第 3、7、11...组参数
```

每个 GPU 只计算一部分，最后再交换结果，这就是 **optimizer sharding**。其中一个 rank 通常就是一个 GPU 对应的训练进程。


> [!TIP]
> **NOTE：** 这里平分的是 ++参数更新本身的计算量++，不是「梯度还没对齐」。无论后面分几个 node / rank 去做 update，++在这之前每张卡上的全局梯度都已经同步过了++。所以集群 node 很多时，每个 node 独立把全部参数更新一遍也不影响正确性：梯度一样，更新后每个 node 上的模型参数也一样。


### 5.2 原来的方法：跨所有 GPU 分片

假设有两个节点，每个节点有 4 张 GPU：

```text
Node 1：GPU 0、1、2、3
Node 2：GPU 4、5、6、7
```

原来把 optimizer 更新分给全部 8 张 GPU：

```text
全部 optimizer 更新
        ↓
分给 8 张 GPU 计算
        ↓
所有 GPU 交换更新结果
```

问题在于，两种通信速度差异很大：

```text
同一节点内部
GPU ← NVLink → GPU
速度非常快

不同节点之间
Node 1 ← InfiniBand → Node 2
速度慢得多
```

节点数量增加后，大量 optimizer 结果需要跨节点传输。此时增加 GPU 虽然减少了每张卡的计算量，却增加了慢速网络通信。

### 5.3 Dyna-2 的方法：只在节点内部 sharding

Dyna-2 改成：

```text
Node 1
└── 4 张 GPU 在节点内部完成全部 optimizer 更新

Node 2
└── 4 张 GPU 也在节点内部完成同样的 optimizer 更新
```

这样会产生一些重复计算，但 optimizer 的分片和结果交换只经过节点内部的高速 NVLink：

```text
旧方案
└── 整体计算量少算一些，但随着node增多，传输同步的延时太大

新方案
└── 每个节点重复计算，但避免慢速跨节点通信
```

在大规模训练中，**多做一点计算，反而比跨节点传输更快**。这之所以可行，正是因为 5.1 里说的前提已经成立：各卡梯度已经对齐，每个 node 用同一份梯度独立更新，得到的参数仍然一致。

### 5.4 为什么叫 topology-aware？

这里的 topology 指 GPU 的连接结构：

```text
GPU 之间的距离
├── 同一节点：NVLink，通信快
└── 不同节点：InfiniBand，通信慢
```

Dyna-2 根据节点数量自动选择策略：

```text
节点较少
└── 跨全部 GPU sharding
    重复计算少，通信压力尚可

节点较多
└── 只在节点内部 sharding
    用少量重复计算换取更少的跨节点通信
```

因此完整逻辑是：

```text
感知 GPU 的连接结构和通信速度
               ↓
选择 optimizer sharding 范围
               ↓
尽量把通信限制在节点内部
```

在达到切换规模后，Dyna-2 报告 optimizer step 相比原来的全局 sharding **平均快约 3 倍**。

> [!NOTE]
> **一句话总结：** 小规模时「少算一点」更值钱；大规模时「少跨节点传数据」更值钱。

![跨整个 job 分片 vs 节点内分片](media/dyna-2-infra/figure10-optimizer-sharding.png "图 10｜论文 Figure 10：optimizer sharding across the job versus inside each node。左侧跨整个 job 分片，broadcast 随 node 数增长，每个结果都走 inter-node fabric；右侧只在节点内分片，traffic 留在 NVLink，各 node 重复计算同一份 update。来源：Dyna Robotics"){.scale85}

![切换规模下三种 sharding 的 optimizer step 耗时与 Muon broadcast](media/dyna-2-infra/figure11-optimizer-step-cost.png "图 11｜论文 Figure 11：measured optimizer step cost by sharding strategy。Unsharded 0.62 s；Hybrid 0.14 s；Fully sharded median 0.18 s、mean 0.47 s（mean 是 median 的 2.6×，cost is all tail）。Muon broadcast：Hybrid 为 1×（NVLink），Fully sharded 为 7.6×（InfiniBand）。同步训练里慢 step 会被每个 rank 一起付，所以要比 mean。来源：Dyna Robotics"){.scale85}

### 6. Job resilience：让大规模训练可以自动应对故障

百万小时训练会占用大量 GPU，并持续运行数周。由于采用同步训练，只要一张 GPU 或一个 rank 出问题，其他 GPU 都必须等待：

```text
一个 rank 失败
      ↓
整个训练 step 无法继续
      ↓
训练任务停止
      ↓
丢失上次 checkpoint 之后的进度
```

节点越多、训练时间越长，遇到硬件或系统故障几乎是必然的。因此 Dyna-2 的思路不是保证“永不出错”，而是：

> **提前排除坏节点，并在故障发生后自动恢复训练。**

**1. Preflight checks：训练前检查节点**

有些节点虽然显示为 healthy，实际可能存在：

```text
GPU ECC 错误
GPU 数量或状态异常
kernel error
本地磁盘异常
container runtime 异常
```

Dyna-2 在任务启动前，由 Slurm 对候选节点进行检查：

```text
训练任务提交
      ↓
Slurm 检查节点
├── GPU inventory
├── GPU error counters
├── kernel log
├── local disk
└── container runtime
      ↓
正常节点 → 参与训练
异常节点 → drain
```



> - drain 的意思是：将节点暂时标记为不可调度，阻止训练任务使用它。
> 
> - Slurm 是大型 GPU 集群的资源管理和任务调度系统。

Dyna-2 使用的是**重启后重新计数的错误指标**，而不是 GPU 的终身错误总数，避免因为很久以前的一次故障永久封禁已经恢复正常的节点。


**2. Auto-restart：训练失败后自动恢复**

故障发生后分两种情况处理：

```text
单个 worker 进程失败
└── 在原位置重新启动 worker

整个训练 job 失败
└── Slurm 自动重新排队
    ↓
   重新分配可用节点
    ↓
   从最近 checkpoint 恢复训练
```

**3. One-click deployment：快速部署新集群**

单个供应商通常无法提供训练所需的全部 GPU，因此 Dyna-2 会使用多个厂商的集群。但不同厂商提供的环境并不相同：

```text
厂商 A：已经安装 Slurm 和 container runtime
厂商 B：只提供基础系统镜像
厂商 C：网络和存储配置不同
```

Dyna-2 使用统一的 **Ansible playbook** 部署集群：

```text
统一 Ansible playbook
          +
各集群自己的 inventory 配置
          ↓
自动安装和配置
├── scheduler
├── container runtime
├── monitoring
└── storage/network
```

这样新增一个集群主要变成修改配置，而不是重新手工搭建，部署时间由数周缩短到数天。

**总结**

```text
训练前
└── Preflight checks：排除异常节点

训练中
└── Auto-restart：进程失败后自动重启

任务失败
└── Requeue + checkpoint：重新调度并恢复进度

集群扩容
└── Ansible：快速部署标准化集群
```

> [!NOTE]
> **一句话总结：** Job resilience 的核心不是避免所有故障，而是让故障能够被提前发现、自动隔离，并在发生后从 checkpoint 自动恢复，避免数周训练因为一个节点失败而彻底中断。

## 关键细节补充：

### 1. 数据库中的metadata，Product DB，和MCAP中的episode数据关系？
> [!TIP]
> 这部分是服务于 [3.3 为什么需要 Warehouse？](#section-16)，这里主要解释了 MCAP、metadata 与 manifest 的关系。

不是新的机器人数据格式。**MCAP 仍然是真正保存 episode 数据的文件**。我前面写的表格只是数据库中的 **metadata（目录信息）**，容易让人误以为数据换了格式。

两者关系是：

```text
真正的数据
└── episode_001.mcap
    ├── /camera_left  → frames
    ├── /proprio      → robot states
    └── /action       → actions

对应的 metadata
└── episode_001
    ├── path       = /data/episode_001.mcap
    ├── task       = folding
    ├── success    = true
    ├── camera_ok  = true
    └── num_steps  = 500
```

整个系统可以理解为：

```text
Object Storage
├── episode_001.mcap
├── episode_002.mcap
└── episode_003.mcap
        ↑
        │ path 指向对应文件
        │
Production DB / Warehouse
├── episode_001 | path | folding | success=true
├── episode_002 | path | folding | success=false
└── episode_003 | path | pick    | success=true
```

它们的分工不同：

```text
MCAP
└── 保存 episode 内部的完整数据
    camera / state / action / timestamp

Database
└── 保存 episode 级别的描述信息
    文件在哪、任务类型、是否成功、质量是否合格
```

SQL 只是在 metadata 中挑选 episode：

```text
Warehouse 中筛选符合条件的 metadata
                    ↓
生成 manifest：episode_id + MCAP path + 时间范围
                    ↓
训练程序根据 path 打开对应的 MCAP
                    ↓
读取 camera / state / action
```

所以没有出现新的数据格式，始终是：

```text
MCAP     = 真正的数据文件
metadata = MCAP 文件的“目录卡片”
manifest = 本次训练选中的“目录卡片清单”
```

### 2. Alluxio 是什么？

> [!TIP]
> 这部分是服务于 [4.3 放到NVMe的数据由Alluxio统一管理](#section-23)，这里主要解释 Alluxio 在训练程序和云存储之间做什么。

Alluxio 是位于 GPU 训练程序与云存储之间的分布式缓存系统：

```text
PyTorch / Training
        ↓
      Alluxio
        ↓
本地缓存
├── Node 1 NVMe
├── Node 2 NVMe
└── Node 3 NVMe
        ↓ 缓存没有时
Cloud Object Storage
```

一次读取过程可以理解为：

```text
训练请求 episode_001.mcap
        ↓
Alluxio 根据路径找到负责节点 Node 2
        ↓
Node 2 的 NVMe 中有对应 page？
    ├── 有 → 直接返回
    └── 没有 → 从云端读取、缓存后返回
```

因此，Alluxio：

```text
不是数据库
不是 MCAP 格式
也不是永久保存数据的主存储

而是：
把多个节点的 NVMe 组织起来
为云端数据提供一个分布式高速缓存层
```

真正可靠、完整的数据仍保存在 cloud storage；即使缓存丢失，也可以重新从云端获取。

> [!NOTE]
> 一句话总结：**Alluxio 根据文件路径把不同 MCAP 分配给不同节点负责，并把实际访问的 pages 缓存在该节点的 NVMe 上，让训练尽量就近读取，而不是反复访问云端。**
